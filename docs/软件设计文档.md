# Base Augment Agent 软件设计文档

> 本文档基于 `src/agent/` 当前实现编写，覆盖系统概览、架构、模块职责、核心数据流、线程/并发模型、资源管理、错误处理、配置体系与扩展点。

## 1. 系统概览

### 1.1 定位

Base Augment Agent 是一个**本地自主 Agent**：

- **本地优先**：所有工具执行、文件操作、知识库向量检索都在本地完成；唯一的外部网络依赖是 LLM API（OpenAI 兼容）。
- **图形界面**：基于 PyQt6 的桌面应用，提供对话、思考过程、日志三栏式交互体验。
- **可插拔工具**：内置 15 个工具（12 个通用 + 3 个 RAG，含 3 个记忆工具、2 个技能工具；`webexec_js` 仅在配置浏览器端点时注册）+ MCP 协议接入远程工具，工具以「类 + schema」形式注册，由模型自主调用。
- **本地 RAG 知识库**：自动解析文档、清洗、切片、向量化、LanceDB 存储、BGE 重排序，全程离线。
- **上下文自管理**：主动摘要 + 被动收缩，避免超出 LLM 上下文窗口；摘要持久化到 `workspace/memory.md`。

### 1.2 技术栈

| 层 | 技术 |
|----|------|
| UI | PyQt6（QMainWindow / QThread / pyqtSignal） |
| LLM 传输 | httpx（流式 SSE） |
| 工具系统 | 自研 `Tool` 抽象 + MCP JSON-RPC over stdio |
| 向量存储 | LanceDB（本地 Lance 列式格式） |
| 嵌入模型 | FastEmbed (ONNX Runtime) — `nomic-ai/nomic-embed-text-v1.5-Q`（Q4 量化，~137MB） |
| 重排序 | FlagEmbedding — `BAAI/bge-reranker-base` |
| 文档解析 | python-docx / openpyxl / python-pptx / PyMuPDF / ebooklib / bs4 / RapidOCR |
| 持久化 | JSON 文件（config / memory / graph / skills / manifest）+ LanceDB（向量索引） |

### 1.3 入口

[main.py](file:///Users/arlenecc/codebase/base-agent/main.py) 将 `src/` 注入 `sys.path`，调用 [agent.ui.main_window.run()](file:///Users/arlenecc/codebase/base-agent/src/agent/ui/main_window.py)，后者构建 `QApplication` + `MainWindow` 进入 Qt 事件循环。

### 2.2 关键设计原则

1. **UI 线程绝不阻塞**：所有耗时操作（LLM 流式调用、RAG ingest、依赖安装、模型列表获取）都在 QThread 中执行；UI 通过 `pyqtSignal` 接收事件。
2. **回调驱动的协议**：Agent 通过 `AgentCallbacks` 抽象与外界通信，UI 层用 `Bridge` 把回调转成 Qt 信号，实现线程安全。
3. **资源显式释放**：ONNX Runtime / LanceDB / MCP 子进程 / httpx 连接都通过 `close()` / `shutdown()` 显式释放，不依赖 Python GC。
4. **协作式取消**：所有长任务都有取消标志（`threading.Event`），在文件/批处理边界检查后退出，不强制 kill。
5. **原子写**：所有 JSON 持久化（config / memory / skills / manifest / memory.md / 文件写入）都使用 temp + `os.replace()` 原子写。
6. **工作区沙箱**：文件工具用 `realpath` 解析并前缀检查，符号链接逃逸也被拒绝；`code_run` 通过 `builtins.open` 守卫拦截工作区外的写操作。

### 3.1 [src/agent/agent.py](file:///Users/arlenecc/codebase/base-agent/src/agent/agent.py) — Agent 推理核心

**职责**：实现一次用户 turn 的完整推理循环。

**关键组件**：
- `AgentCallbacks`（[L21-41](file:///Users/arlenecc/codebase/base-agent/src/agent/agent.py#L21-L41)）：定义所有 UI 钩子（`on_content` / `on_reasoning` / `on_tool_start/end` / `on_log` / `on_usage` / `on_token_speed` / `on_skill_suggested` / `on_error` / `on_context_shrunk` / `confirm` / `ask_user` / `on_finished`）。
- `SYSTEM_PROMPT`（[L48-61](file:///Users/arlenecc/codebase/base-agent/src/agent/agent.py#L48-L61)）：精简的固化系统提示（~200 tok），含操作原则、确认策略、工具调用约定、记忆/技能/RAG 使用引导。
- `_estimate_tokens`（[L79-102](file:///Users/arlenecc/codebase/base-agent/src/agent/agent.py#L79-L102)）：CJK / 非 CJK 分段估算 token 数，用于实时速度显示和上下文收缩判定。
- `Agent.run`（[L417-687](file:///Users/arlenecc/codebase/base-agent/src/agent/agent.py#L417-L687)）：核心循环，详见 §4.1。

**配置参数**：
- `max_iterations`（默认 15）：每个 turn 最多推理迭代数。
- `max_history`（默认 50）：历史消息条数上限（超出则裁剪，且不会留下悬挂 `tool` 消息）。
- `max_context_tokens` / `context_shrink_ratio`：上下文收缩阈值。
- `_max_shrinks_per_run = 3`：单次 run 收缩次数上限，防止错误配置下的死循环。
- `_shrink_keep_recent = 6`：收缩时保留的最近消息数（当前任务上下文）。

### 3.2 [src/agent/llm_client.py](file:///Users/arlenecc/codebase/base-agent/src/agent/llm_client.py) — LLM 流式客户端

**职责**：通过 OpenAI 兼容 API 进行流式 chat completions。

**关键设计**：
- 单一 `httpx.Client` 实例（连接池复用）。
- **结构化超时**：`httpx.Timeout(connect=timeout, read=max(timeout,60), write=timeout, pool=timeout)`——`read` 是流式响应**每个 chunk 之间的最大间隔**。纯 `timeout=float` 只约束整请求（流式下首字节到达后即失效），本地模型生成中途卡住会让 `iter_lines()` **无限阻塞**（表现为「回复到一半停住不动」）；设置 read 超时后最多等 60s 就抛 `httpx.ReadTimeout` 而非永久卡死。
- `chat_stream`（[L88-166](file:///Users/arlenecc/codebase/base-agent/src/agent/llm_client.py#L88-L166)）：
  - 解析 SSE `data:` 行，跳过 `[DONE]`。
  - 累积 `delta.tool_calls`（按 `index` 分桶拼接 `function.name` / `function.arguments`）。
  - 支持 DeepSeek 风格的 `reasoning_content` 字段。
  - 末尾发射 `StreamEvent(type="done", tool_calls=..., usage=...)`，其中 `usage` 来自 `stream_options.include_usage=True`。
- 透传 `min_p` / `top_k` / `repetition_penalty` 等本地模型常用参数。

### 3.3 [src/agent/tools/](file:///Users/arlenecc/codebase/base-agent/src/agent/tools) — 工具系统

#### 3.3.1 [base.py](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/base.py) — 注册中心

**`Tool` 抽象**（[L29-58](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/base.py#L29-L58)）：
- `name` / `description` / `parameters`（JSON Schema） / `destructive`（是否需要确认）。
- `should_confirm(args)`：默认 `return self.destructive`，可重写实现细粒度策略。
- `schema()`：转为 OpenAI function-calling 格式。

**确认消息（`Agent._confirm_message`）**：`code_run`/`shell_run` 的确认弹窗**只显示用途说明，不贴代码/命令全文**（避免超长文本把 Yes/No 按钮顶出屏幕）：
- **启发式优先（零延迟）**：代码提取顶部注释/docstring/函数名/包安装命令；命令走内置映射（pip/npm/git/rm/docker 等）→ 人类可读用途（`_summarize_code` / `_summarize_command` / `_looks_like_command`）。绝大多数模型生成的代码带注释，走此路径即时返回。
- **LLM 兜底**：仅当启发式得到泛化描述（如「执行代码片段：xxx」、未知命令）时，`_describe_code_purpose` 才用独立抽取客户端生成 ≤20 字中文用途——避免每次确认都同步阻塞 1-3s。
- UI 兜底：`_on_confirm_request` 对消息截断到 800 字符。

**`ToolRegistry`**（[L61-233](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/base.py#L61-L233)）：
- `__init__` 中 `_register_defaults()` 注册 12 个默认内置工具（含 3 个 memory 工具、2 个 skill 工具）+ RAG 工具 + MCP 工具；`webexec_js` 仅在 `browser_endpoint` 配置时注册（省 ~146 tok schema）。
- `reload_rag()`：同步完成后刷新 agent 的 LanceDB 表句柄。
- `shutdown()`：停止所有 MCP 子进程，释放 RAGEngine 资源、LongTermMemory 单例与 SkillIndex 单例。
- `execute(name, args)`：捕获 `TypeError`（参数不匹配）和未预期异常，统一返回 `ToolResult`。

**`parse_args`**（[L236-251](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/base.py#L236-L251)）：解析 JSON 参数；空串返回 `{}`，非空但非法 JSON 抛 `ValueError`（让模型看到错误而非被当作 `{}` 误诊）。

#### 3.3.3 [mcp_client.py](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/mcp_client.py) + [mcp_tool.py](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/mcp_tool.py) — MCP 协议

**`MCPClient`**：管理一个 MCP server 子进程。
- 启动 `subprocess.Popen`，stdin/stdout 走 JSON-RPC 2.0。
- **双锁设计**（[L61-66](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/mcp_client.py#L61-L66)）：
  - `_lock`：保护 `_pending` / `_results` / `_request_id`。
  - `_write_lock`：保护 stdin 写入，避免并发 `_call()` 在管道上交错字节（>PIPE_BUF 不原子）。
- **reader 线程**（[L267-313](file:///Users/arlenecc/codebase/base-agent/src/agent/tools/mcp_client.py#L267-L313)）：持续读 stdout，按 `id` 分发到 `_results` 并 `event.set()`；退出时给所有 pending 请求回填错误响应。
- **stderr drain 线程**：防止管道缓冲区满导致子进程阻塞。
- **生命周期**：`start()` 做 `initialize` 握手 + `notifications/initialized` + `tools/list`；`stop()` 关闭 stdin、`terminate()`、5s 超时后 `kill()`、唤醒所有 waiter。

**`MCPTool`**：把 MCP 工具定义包装为 `Tool` 子类；`inputSchema` → OpenAI parameters；默认 `destructive=True`（外部工具需确认）。

### 3.4 [src/agent/memory.py](file:///Users/arlenecc/codebase/base-agent/src/agent/memory.py) — 记忆存储

**`_JsonStore`**（[L16-121](file:///Users/arlenecc/codebase/base-agent/src/agent/memory.py#L16-L121)）：
- 线程安全（`threading.Lock`）的 JSON KV 文件存储。
- **防抖写入**：`set()`/`delete()` 只标记 `_dirty`，满 0.5s 才落盘，避免循环里 O(N²) I/O。
- 原子写（temp + `os.replace`）。
- `reload()`：从磁盘重新加载，用于跨线程/跨进程同步。
- `atexit` + `weakref`：进程退出时强制 flush 防丢数据。

**`WorkMemory`**：键值对记事本（`workspace/.agent/work_memory.json`）。短期记忆，分两类内容：
1. **模型手动 scratchpad**：任务跨步骤间记中间结果和计划（`work_memory` 工具的 set/get/list/clear）。
2. **当天自动抽取事实**：`_append_daily_facts()` 在事实抽取后把 observation 同步写入保留键 `__auto_facts__`（`{"date": "YYYY-MM-DD", "facts": [...]}`）。只保留当天，跨天后自动重置（历史已在长期记忆图谱中，靠 `memory_search` 检索）。对话时只把当天事实注入上下文。

**`LongTermMemory`**（知识图谱版）：长期记忆采用知识图谱架构，数据模型为实体（Entity）+ 关系（Relation）+ 观察（Observation），模仿 Memory MCP Server 的设计模式。

- **底层存储**：`GraphMemoryStore`（[graph_memory.py](file:///Users/arlenecc/codebase/base-agent/src/agent/graph_memory.py)），JSON 文件持久化图谱结构 + LanceDB 存储观察向量。
- **文件**：`workspace/.agent/long_memory.graph.json`（图谱 JSON）+ `long_memory.graph.json.vectors/`（LanceDB）。
- **语义检索**：观察通过 `nomic-embed-text-v1.5-Q` 嵌入后存入 LanceDB，`search()` 支持向量语义检索；向量索引不可用时回退到关键词子串匹配。
- **自动事实抽取**：`extract_facts_via_llm()` 调用 LLM 从对话文本中抽取实体/关系/观察，返回结构化 JSON。
- **兼容 API**：保留 `add()` / `add_many()` / `all()` / `search()` / `clear()` 接口，旧代码无需改动；扁平事实作为 "General" 实体的观察存储。
- **迁移**：首次加载时自动将旧 `long_memory.json` 的扁平事实列表迁移到图谱。
- **按需检索（不注入）**：长期记忆不注入 prompt，模型通过 `memory_search` 工具按需语义检索；`snapshot(max_items=10)` 仅作调试/`memory_graph snapshot` 操作返回紧凑摘要。

### 3.4.1 [src/agent/graph_memory.py](file:///Users/arlenecc/codebase/base-agent/src/agent/graph_memory.py) — 知识图谱引擎

**`GraphMemoryStore`**（[L55-320](file:///Users/arlenecc/codebase/base-agent/src/agent/graph_memory.py#L55-L320)）：

线程安全的知识图谱存储，支持 CRUD + 语义检索。

**数据模型**：
```
entity    = {name, type, observations: [str], created_at}
relation  = {source: name, target: name, label: str}
```

图以实体 name（大小写不敏感）为主键，创建同名实体自动合并观察。

**CRUD 方法**：
| 方法 | 说明 |
|------|------|
| `create_entity(name, type?, observations?)` | 创建/合并实体 |
| `delete_entity(name)` | 删除实体及其所有关系 |
| `add_observations(name, observations)` | 添加观察（实体不存在则自动创建） |
| `create_relation(source, target, label)` | 创建有向边，自动创建两端实体 |
| `get_entity(name)` / `list_entities()` | 查询 |
| `search(query, top_k=8)` | 语义检索观察 |
| `snapshot(max_items=10)` | 精简文本摘要 |
| `clear()` / `close()` | 清空 / 释放资源 |

**向量索引**（懒初始化 + 双重检查锁）：
- 首次 `search()` 或索引观察时初始化 LanceDB + FastEmbed，`_vec_lock` + 双重检查防止并发重复加载。
- **Embedding 模型共享**：通过 `get_or_create_embedding_function()` 获取进程级单例，与 RAG VectorStore 共用同一 ONNX 模型（~137MB），避免加载两份。
- **锁外批量索引**：`create_entity` / `add_observations` 在锁内收集 `to_index` 列表，释放 `_lock` 后调用 `_index_observations_batch()`——用 `embed_documents()` 将整批观察在**单次 ONNX 前向**中完成嵌入（替代逐条 `embed_query()`，N 条观察从 N×10-50ms 降为一次批量计算），避免 ONNX 计算阻塞 JSON 读取。
- **非对称嵌入前缀**：观察作为检索目标用 document 前缀嵌入（`embed_documents`），查询侧用 query 前缀（`embed_query`），符合 nomic 模型的非对称检索要求（此前观察误用 query 前缀，已修正）。
- 非致命：LanceDB/FastEmbed 不可用时，`search()` 回退到关键词匹配。
- 观察 upsert：用 `entity|observation` 的 md5 hash 做主键，先 delete 再 add。
- 删实体时 `_deindex_observations()` 批量删除该实体所有向量；实体名的单引号做 SQL 转义（`'` → `''`），防止 filter 表达式被畸形/注入（实体名来自 LLM，不可信）。
- `close()` 不 release 共享 ONNX session（仅解除引用），因为 RAG 可能仍在使用。

**`extract_facts_via_llm(llm, conversation)`**（[L330-380](file:///Users/arlenecc/codebase/base-agent/src/agent/graph_memory.py#L330-L380)）：

调用 LLM 从对话文本抽取实体/关系/观察。

### 3.5.1 [src/agent/skill_index.py](file:///Users/arlenecc/codebase/base-agent/src/agent/skill_index.py) — 技能索引

**`SkillIndex`**：扫描 `.agent/skills/` 目录，把所有技能元数据汇总为一张 `_index.json` 索引表，供 `skill_search` 工具 O(1) 加载检索。

**目录约定**：
```
.agent/skills/
├── _index.json            ← 自动生成的索引（原子写：tmp + os.replace）
└── <skill-name>/
    ├── skill.json         ← 必需：{name, description, keywords, tags, entry}
    └── prompt.md          ← 默认 entry 文件（指令全文）
```

**关键设计**：
- **防抖扫描**（`_should_scan`）：满足任一条件才重建索引——从未扫描 / 距上次超过 `_SCAN_INTERVAL`（300s）/ 技能目录 mtime 变化。加载已有索引时同步 `_last_dir_mtime`，避免启动后立即重扫。
- **宽容跳过**：无 `skill.json`、JSON 损坏、缺 `name`、entry 文件不存在、隐藏目录（`.` / `_` 前缀）都跳过并记 warning，不中断整体索引。
- **加权检索**（`search`）：name 命中 ×3、keywords ×2、tags ×2、description 子串 ×1，按总分降序返回 top_k。
- **路径穿越防护**（`_resolve_within`）：`read_skill_content(path, entry)` 的参数来自 LLM，`realpath` 解析后做前缀检查，拒绝 `..`、绝对路径、符号链接逃逸。
- **线程安全**：扫描与读取均在 `_lock` 保护下进行。
- **单例**：实例缓存在 `ToolRegistry._skill_index` 上（由 `skill_search` / `skill_load` 懒创建），`ToolRegistry.shutdown()` 解除引用。

### 3.5.2 [src/agent/skill_retriever.py](file:///Users/arlenecc/codebase/base-agent/src/agent/skill_retriever.py) — SKILL.md 混合检索

对 `workspace/skills` 下的 **SKILL.md** 文件做语义 + 全文混合检索，供 `skill_semantic_search` 工具使用。

**扫描与解析**：
- `SkillScanner`：递归 `os.walk` 扫描所有 SKILL.md，跳过 `tests/`/`test/`/`__pycache__`/隐藏目录；防抖扫描（目录 mtime 变化或 300s 间隔）。
- `parse_skill_md`：解析 YAML frontmatter（手写轻量解析，不依赖 PyYAML）——`name`/`description`/`tags`（支持 `[a, b]` 流式数组与逗号分隔）；解析正文段落——`## When to Use This Skill`（适用）、`## When NOT to Use`（不适用）、`## Examples`（示例）。

**向量化与建表**（`SkillVectorStore`）：
- 用共享的 nomic-embed-text 分别对 `description` 与 `examples`（无 examples 时回退 when_to_use/description）计算向量，批量两次前向。
- LanceDB 表 `skills` 列：`dir`（SKILL.md 所在目录）、`name`、`tags`、`description`、`desc_vec`（description 向量）、`examples_vec`（examples 向量）、`combined`（name+tags+description+examples 拼接原文）、`combined_fts`（jieba 预分词，供 BM25）。
- 显式 pyarrow schema 声明向量列为 `list(float32)`，避免 LanceDB 把 `list[float]` 误推断为标量 Float64。
- 向量归一化后入库，用 L2 距离模拟余弦相似度（`1 - d²/2`）。
- **小批次构建（防内存爆炸）**：`build()` 以 `batch_size=8` 分批 embed + `table.add()`，每批完成后释放；`description`/`examples`/`combined` 分别截断至 2000/3000/6000 字符（SKILL.md 的 Examples 段落可达数十 KB，整段 embed + 分词会放大内存与耗时）。实测 2757 个 skill 全量索引：峰值 RSS **4.19 GB**、耗时 12.4 分钟；此前一次性处理全部文本时峰值达 65 GB 导致系统卡死。

**混合检索**（`SkillRetriever.retrieve`）：
1. 向量检索：分别对 `desc_vec`、`examples_vec` 检索，两通道按 **0.6:0.4** 加权融合（同一技能两通道都命中时，相似度按比例融合成一个分数）；取 3 候选。
2. BM25 全文检索 `combined_fts`：取 3 候选。
3. 去重（按 `dir`）；向量分数为统一排序依据（BM25 命中的技能若未在向量候选中，补查其向量相似度作为 score）。
4. 剔除相似度 < 0.5 的候选。
5. 返回候选的 name+tags+description，由 agent（大模型）判断选用哪个，再 `skill_load` 读取 SKILL.md 及目录下 references/scripts 支持文件。

**资源管理**：`SkillRetriever` 单例挂在 `ToolRegistry._skill_retriever`，`shutdown()` 关闭 LanceDB 连接（不关闭共享的 embedding 单例）。

#### 3.6.4 [chunker.py](file:///Users/arlenecc/base-agent/src/agent/rag/chunker.py) — 分片编排 + 递归切片

```
hybrid_chunk_text  →  semantic_chunk_text  →  chunk_text（递归）

#### 3.6.5 [hybrid_chunker.py](file:///Users/arlenecc/base-agent/src/agent/rag/hybrid_chunker.py) + [semantic_chunker.py](file:///Users/arlenecc/base-agent/src/agent/rag/semantic_chunker.py) — Hybrid 分片

**Hybrid 分片**（结构 + 语义），分片大小：最小 100 / 最大 800 tokens / overlap 10%：

```
Markdown 文本
  ├─ _split_by_structure()：按 #~###### 标题 + 空行段落边界切分
  ├─ 超长章节（>800 tokens）→ semantic_chunk_text()（chonkie 语义细分）
  ├─ _merge_to_target_size()：合并过小块至 ≥100 tokens
  └─ _apply_overlap()：相邻块 10% overlap（句子边界对齐）
```

- **语义分块**（`semantic_chunker`）：chonkie `SemanticChunker` + `threshold=0.7` 按语义相似度切分；CJK 分隔符（`。！？；，`）避免整段中文当一句。
- **嵌入复用**：`_ChonkieEmbeddingAdapter` 继承 chonkie `BaseEmbeddings`，包装进程级 nomic-embed-text 单例——语义分块与向量存储**共用同一份 ~137MB ONNX 模型**，不重复加载。
- **overlap 句子对齐**（`_tail_by_tokens`）：按句子边界倒序取尾部，绝不切断句子。
- **三级回退**：chonkie 未安装 → 语义分块返回 `None` → 递归分块兜底，任何环境都能工作。

#### 3.6.6 [vector_store.py](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py) — 向量存储

**`FastEmbedEmbeddingFunction`**：
- `nomic-ai/nomic-embed-text-v1.5` via ONNX Runtime，~130MB 量化后，离线可用。
- **文档/查询前缀**：`search_document: ` / `search_query: `（nomic 模型要求）。
- `embed_documents(texts)`：批量文档嵌入——整批文本在**单次 ONNX 前向**中完成，远快于逐条 `embed_query()`；RAG 切片入库与知识图谱观察批量索引共用此路径。
- 懒加载，首次调用才下载模型。

**`VectorStore`**（[L76-660](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py#L76-L660)）：
- **存储列**：每切片存入 `vector`（nomic-embed-text 向量）、`text`（完整原文）、`source`（来源文件名）、`chunk_index`（切片编号）、`text_fts`（jieba 预分词，BM25 索引列）。
- **BM25 全文索引**（`_ensure_fts_index` + `_tokenize_for_fts`）：`text_fts` 列用 jieba 分词后空格连接，原生 FTS `simple` tokenizer 索引。采用 Python 层 jieba 预分词 + simple 索引的业界标准做法（规避中文无空格无法分词）。索引在每次 add 后 `replace=True` 重建（LanceDB 的 FTS 索引不会自动增量更新）。`_ensure_fts_index` 兼容 lancedb 0.25（`create_fts_index(use_tantivy=False)`）与 0.37（`create_index(config=FTS)`）两种 API。
- **文档元数据表**（`_documents_table`，Meta-context RAG）：`doc_name`（文档名）/ `digest`（缩略版本：目录结构 + 章节标题）/ `markdown`（完整 Markdown）/ `chapters`（章节结构 JSON）。`upsert_document` 按 `doc_id`（文档名 md5）upsert；`get_document_digest` 支持精确/部分标题匹配；表懒创建用 `_documents_lock` 双重检查锁保护（多 worker 并发 ingest 时防 `create_table` 竞态）。documents 表内容有内存缓存（`_documents_cache`），`get_document_digest`/`list_documents` 不重复全表 `to_pylist()`；`upsert_document` 的 delete+add 与 `delete_document` 在 `_documents_lock` 下串行化，避免并发写入交错。
- **`_ensure_table()`**：每次调用都重查 `table_names()`（不缓存"表不存在"），因为 SyncKnowledgeWorker 可能已创建表。
- **`add_streaming`**（[L254-411](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py#L254-L411)）：流式写入，内存占用 O(batch_size) 而非 O(总 chunks)。
  - 第一批特殊处理：决定是 `create_table` 还是 `add` 到已有表。
  - 已有表：按 source 的 md5 hash 用 `id LIKE '{hash}_%'` 删除旧记录（upsert 语义）。
  - 批量 20 条/批。
- **`_embed_chunks`**：将每批 20 个 chunk 再拆分为 5 条/子批进行 embedding，每个子批次完成后 `time.sleep(0.01)` 释放 GIL，让主线程的 QTimer 有机会轮询日志缓冲区并更新 UI。ONNX Runtime 的 `embed()` 在 C++ 计算期间持有 GIL，整批一次性嵌入会导致 UI 长时间冻结。
- **`search`**：向量归一化为单位长度后用 L2 距离模拟余弦相似度；`_distance` 转换为 `[0,1]` 相似度分数。
- **`search_fts`**：BM25 关键词检索（原生 FTS `simple` tokenizer + jieba 预分词），支持 `where` SQL 过滤。
- **`search_with_rerank`**：混合检索——向量 `top_k×4` + BM25 `top_k×4`（两者都应用 `where` 过滤）→ 按 (source, chunk_index) 合并去重 → BGE reranker 精排 → 过滤相似度 < 0.7 → 返回 ≤ top_k。
- **`rerank`**：BGE 不可用时回退到距离排序；分数归一化到 `[0,1]`。有 reranker 时按 `min_similarity=0.7` 过滤（回退模式不强制过滤，因距离分数语义不同）。
- **`_get_reranker`**：懒加载 BGE reranker，含 numpy 版本探测——macOS Intel 上 torch 最高 2.2.2（需 numpy 1.x），numpy 2.x 下 `tensor.numpy()` 抛 `Numpy is not available`；检测到 numpy>=2 时提前降级为向量距离排序并给出清晰日志，避免模型加载崩溃。加载用 `_reranker_state` 状态机（idle/loading/done/failed）去重并发加载线程。
- **`_check_schema_migration`**：旧表缺少 `text_fts` 列时自动迁移——`to_arrow().to_pylist()` 读旧数据（无 pandas 依赖），drop 旧表后重建并回填 `text_fts` 列。
- **`close()`**（[L571-623](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py#L571-L623)）：
  - 显式调用 ONNX `InferenceSession.release()` 立即回收 C++ 堆。
  - BGE reranker 的 PyTorch 模型 `model.cpu()` 后置 None。
- **`reload()`**：丢弃表句柄，下次操作重新打开。

#### 3.6.7 [document_outline.py](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/document_outline.py) — Meta-context RAG（目录结构提取）

**`document_outline`**（目录结构提取，不生成逐章摘要）：

缩略版本（digest）只包含文档的**目录结构（标题层级）**，不包含逐章摘要。逐章 LLM 摘要慢、费 token、且对本地模型易产生空结果，标题层级已足以支撑定向检索。提取策略按优先级：

1. **标准 Markdown 标题**（`extract_chapters`）：按 `#`~`######` 层级切分章节树，正文前文本作为「前言」。
2. **纯文本启发式**（`extract_chapters_plain`，无 `#` 标题时回退）：
   - **目录块识别**（`_extract_from_toc_block`）：定位 `目录`/`目 录`/`Contents`/`Table of Contents` 标记，收集其后一行一个标题的条目，遇到正文句（以句末标点结尾）终止。

   - **编号标题**（`_numbered_match`）：`1.`/`1.1`/`1.1.1`。
   - **EPUB 链接**（`_normalize_title`）：`[TITLE](#anchor)` → `TITLE`。
   - **全大写短行**（`_ALLCAPS_RE`）：英文 EPUB 章节标题，要求前后空行降低误判。
- `build_digest`：先尝试 Markdown 标题，无结果回退纯文本启发式，输出 `# 目录\n...`；`build_and_store_digest` 在完全无标题时兜底为文档名（避免空目录）。

**增量重刷**（`RAGEngine.ensure_digests_for_cached_documents(refresh_stale=True)`）：

**检索闭环**（Meta-context + Targeted RAG）：

#### 3.7.1 日志显示架构

知识同步期间的日志显示采用 **QTimer 轮询 + 线程安全日志缓冲区** 方案，而非传统的 Qt queued signal：

**两条日志通道**：
1. **QSignalLogHandler**（常态）：挂在 root logger 上，通过 `message_received` pyqtSignal 将日志安全传递到 UI 线程的 `log_view`。用于 Agent 对话、工具执行等常态日志。
2. **`_log_buffer` + QTimer 轮询**（同步期间）：同步期间 `QSignalLogHandler._sync_active=True`，跳过 RAG 日志避免与轮询并发操作 `log_view` 导致崩溃。RAG engine 通过 `log_callback` 参数直接把日志写入 `_log_buffer`（`threading.Lock` 保护），主线程的 `QTimer` 每 100ms 轮询消费 buffer 并 `appendPlainText`。

**为什么不用 Qt queued signal**：ONNX Runtime 在 `embed()` 期间持有 GIL 做 C++ 计算，Qt 的 queued signal 需要主线程事件循环处理，但 GIL 被占用时事件循环无法执行。QTimer 的 `timeout` 回调也是在主线程事件循环中执行的，但只要 `_embed_chunks` 的子批次 `sleep(0.01)` 短暂释放 GIL，QTimer 回调就能插入执行并消费 buffer。

**分工**：
- **日志区域**（`log_view`）：显示详细的全链路日志（扫描→对比→解析→清洗→切片→向量化→清理→保存）。
- **底部状态栏**（`status_label`）：只显示进度摘要（如"同步中 3/4 (75%) — 已写入 80 切片"），不显示完整日志行，避免重复。

## 4. 核心数据流

### 4.1 Agent 推理循环

```
用户输入
  │
  ▼
Agent.run(user_input)
  │
  ├─ skills.record_request(text)  ──→ 可能触发 on_skill_suggested
  ├─ history.append({user, content})
  ├─ _trim_history()  (max_history 上限，且不留下悬挂 tool 消息)
  │
  └─ while iteration < max_iterations:
       │
       ├─ [主动收缩] 若 _should_shrink_context() (estimate > 90% max_context_tokens):
       │     _shrink_context("主动收缩")
       │     continue   ← 不消耗 iteration
       │
       ├─ messages = [system_prompt] + history
       │   (system_prompt ~200tok + 条件注入: KB状态(仅RAG可用时) /
       │    work_memory(手动scratchpad + 当天自动抽取事实列表) / matched skill)
       │    ※ 长期记忆不注入，靠 memory_search 工具按需检索
       │
       ├─ for ev in llm.chat_stream(messages, tools, temperature):
       │     ├─ "content"   → on_content(ev.content) + 累积 live_est_tokens
       │     ├─ "reasoning" → on_reasoning(ev.content)
       │     └─ "done"     → tool_calls, usage
       │   每 0.3s 发射一次 on_token_speed（用 generation 时间，排除 TTFB）
       │
       ├─ [被动收缩] 若 LLM 抛 context_length_exceeded:
       │     _shrink_context("被动收缩")
       │     iteration -= 1; continue   ← 不消耗 iteration，重试同一次
       │
       ├─ 累积 token 统计（API reasoning_tokens 优先，否则用估算值）
       │
       ├─ assistant_msg = {role: assistant, content, tool_calls}
       │   (补全缺失的 tool_call.id，用 call_{counter}_{idx})
       │   history.append(assistant_msg)
       │
       ├─ if no tool_calls:
       │     _maybe_extract_facts_async(final_content)  ← daemon线程, best-effort LLM 抽取
       │       一次抽取 → 长期记忆图谱 + 短期记忆当天桶(__auto_facts__) 双写
       │     on_finished(); return content
       │
       └─ for tc in tool_calls:
            ├─ parse_args(raw_args)  ← 失败时报错给模型
            ├─ tool = registry.get(name)
            ├─ if tool.should_confirm(args) and not callbacks.confirm(msg):
            │     result = ToolResult(False, "User denied")
            ├─ else:
            │     on_tool_start(name, args)
            │     result = registry.execute(name, args)
            │     on_tool_end(name, result)
            └─ history.append(_tool_message(tc, result))   ← role=tool, tool_call_id 匹配

  (达到 max_iterations 或无 tool_calls 时退出)
```

**关键设计点**：
- **收缩不消耗 iteration**：用 `iteration -= 1` 让被动收缩重试同一轮；主动收缩用 `continue` 跳过本次循环（`iteration` 还未自增）。
- **`_shrink_keep_recent = 6`**：保留最近 6 条消息 verbatim；若切分边界落在 `assistant(tool_calls)` 之后，会把对应的 `tool` 结果拉回保留段，避免悬挂 `tool` 消息。
- **摘要持久化**：写入 `workspace/memory.md`（带时间戳 + 触发原因），原子写。
- **LLM 摘要失败回退**：`_fallback_summary` 用结构化摘要（用户请求 + 工具名列表），不丢工具调用轨迹。
- **Token 估算策略**：API 报告 `reasoning_tokens` 时信任 API；否则用 `_estimate_tokens(reasoning_text)` 估算并加到 total 上。

### 4.2 RAG 摄取流水线

```
ingest(force, progress_callback)
  │
  ├─ Step 1: 扫描 kb 目录 (rglob) → all_files
  │
  ├─ Step 2: 加载 manifest，分片
  │   ├─ 未修改（mtime + size 一致）→ 跳过，progress 回调
  │   └─ 新增/修改 → files_to_process
  │
  ├─ Step 2.5: 按**文件指纹**去重（size + 头/中/尾各 64KB 采样 sha256）
   │   同指纹的多个路径只保留一个规范源，其余标记 duplicate_of（不解析）
   │
   ├─ Step 3: 启动 worker 池（默认 4 线程，文件数不足时按文件数缩减）
   │   （同时起心跳线程：默认每 60s 报「已完成 N/M + 在办文件及耗时」）
   │   每个 worker 处理一个 file shard:
  │     ├─ _extract_with_docling(filepath)  ← 优先 docling, 回退 per-format
  │     │     docling 输出 Markdown 时跳过 clean/normalize
  │     ├─ 若 markdown 缓存有效（mtime ≤ 源文件）→ 读缓存
  │     │   否则 clean_text + normalize_markdown → 写 .md 缓存
  │     ├─ chunk_documents → doc_chunks（hybrid → semantic → recursive）
  │     ├─ 背压: q.put(item, timeout=2.0)  ← 队列满时阻塞
  │     └─ finally: q.put(_SENTINEL)
  │
  ├─ Step 4: 主线程消费队列
  │   _chunk_iter() 生成器:
  │     while sentinels_seen < num_workers:  ← 等于实际启动的线程数
  │       item = q.get(timeout=2.0)
  │       if item is _SENTINEL: sentinels_seen++; continue
  │       更新 manifest[filepath] = signature + content_hash + chunk_count
  │       for c in doc_chunks: yield c
│   store.add_streaming(_chunk_iter(), batch_size=20, on_batch)
│     ├─ 第一批: 决定 create_table 还是 add
│     ├─ 按 source hash 删除旧记录 (upsert)
│     └─ 每 20 条 embed + add 一次（内部再拆分 5 条/子批，子批间 sleep 释放 GIL）
  │
  ├─ Step 5: _cleanup_deleted_files
  │   manifest 中存在但 all_files 不存在的 → store.delete_by_source + 移除 manifest 条目
  │
  ├─ Step 5.5: _cleanup_duplicate_content（按 content_hash 清洗副本向量）
  │   同 content_hash 的多来源只留规范源，其余清向量/digest/缓存并在 manifest 标记
  │
  └─ Step 6: _save_manifest (原子写)
      （Step 5~7 整体在 try/finally 内：finally 无条件停心跳与内存采样线程）
```

**关键设计点**：
- **背压机制**：`queue.Queue(maxsize=parallel_workers * 2)`，worker 超前产出时阻塞，避免内存堆积。
- **取消传播**：`_cancelled` 在 worker put 循环、主线程 get 循环、extract 前等多处检查；`store.add_streaming` 失败时主动 `cancel()` 让 worker 停止产出。
- **Sentinel 丢失保护**：若所有 worker 已退出但 sentinels 未收齐，主线程退出避免死锁。
- **Markdown 缓存**：基于源文件 mtime 判断是否需要重新解析，避免重复 OCR/PDF 解析。
- **日志实时显示**：`ingest()` 接受 `log_callback` 参数，engine 内部 `_log()` 辅助函数同时写 `logger.info()` 和 `log_callback`。`log_callback` 把日志写入 `_log_buffer`（Lock 保护），主线程 QTimer 每 100ms 消费。每个关键节点（解析/清洗/切片前后、批次写入）后调用 `_flush_logs()`（`progress_callback(-1,...)`）触发额外的 UI 刷新机会。
- **资源释放时机**：`SyncKnowledgeWorker.run()` 在 `finally` 中 `engine.close()` 后才 `emit sync_finished`，避免主线程 `reload_rag()` 与 worker 侧资源释放竞态。close 后须置 `self._engine = None`，否则关窗路径会拿到一个已 close 的引擎再关一次。
- **心跳线程**（可观测性）：大文件转换一次几十秒到数分钟，期间日志静默。Step 3 起一条 daemon 心跳线程，每 `_HEARTBEAT_INTERVAL_S`（默认 60s，`RAG_HEARTBEAT_S` 可调，0 关闭）输出「已完成 N/M + 当前在办文件及各自耗时」。据此可区分三种卡住：心跳持续且在办时间上涨（正常只是慢）/ 在办 0 个（向量化收尾中）/ 心跳停止（主线程卡死或进程被杀）。**它必须在异常路径也停下来**——所以 Step 5~7 整体包在 `try/finally` 里，`finally` 中 `_hb_stop.set()`（并 join 内存采样线程）；旧实现只在两条正常 `return` 前停，任一步抛异常就让线程带着 `_inflight`/`stats`/`stats_lock` 闭包活到进程结束。
- **副本去重分三层**：解析前按**文件指纹**（Step 2.5，省掉整段解析/切片/向量化）、入库后按 `content_hash`（Step 5.5，清新增副本向量）、存量重复由独立的「向量去重」按钮扫描清理（保留 `ingested_at` 最早的一份）。前两层只作用于本次同步，存量重复不会被动清理，故第三层必须能单独触发。

### 4.3 RAG 检索流程

```
Agent tool_call: rag_search(query, top_k=3)   ← top_k 封顶 3（#132）
  │
  ▼
RagSearchTool.run(query)
  │
  ▼
RAGEngine.search(query, top_k)
  │
  ▼
VectorStore.search_with_rerank(query, top_k=3, candidate_multiplier=4, min_similarity=0.7)
  │
  ├─ 向量检索: VectorStore.search(query, top_k=12)
  │   ├─ _ef.embed_query(query)  ← 加 "search_query: " 前缀
  │   ├─ _normalize(query_vec)
  │   └─ table.search(query_vec).limit(12).to_list()
  │       → 转换 _distance 为 similarity ∈ [0,1]
  │
  ├─ BM25 检索: VectorStore.search_fts(query, top_k=12)
  │   ├─ _tokenize_for_fts(query)  ← jieba 分词
  │   └─ table.search(tokenized, query_type="fts").limit(12).to_list()
  │       → BM25 分数 (_score)
  │
  ├─ 合并去重: 按 (source, chunk_index) 去重，向量候选优先
  │
  └─ VectorStore.rerank(query, candidates, top_k=3, min_similarity=0.7)
      ├─ BGE reranker 可用: reranker.compute_score([[q, c["text"]]...], normalize=True)
      │   └─ _filter_by_similarity: 过滤 rerank_score < 0.7
      ├─ 不可用: 回退到距离分数排序（不强制 0.7 过滤）
      └─ 按 score 排序取 ≤ top_k
```

**Token 控制**：默认 3 条结果，单次 ≤ 1500 tokens（32768 上下文中占比 < 5%）。

**重排延迟约束（#132）**：v2-m3-int8（568M）在本机 CPU 逐对 ~0.55s/对是实测地板（批并行无收益——CPU EP 单序列已吃满多核；threads ±10% 噪声；截断 512 对 top3 常规场景无收益，不采用）。候选数 = top_k × 4 × 2 路，故 rag_search 的 top_k 在工具层封顶 3（LLM 传 5 曾致 40 条 ≈ 23s）。当前 top_k=3 → 24 条 ≈ 14s，进一步降耗备选（multiplier 4→2 候选池减半、异步重排先回向量序后精化）留观察后决定。

```

### 4.5 工具分发流程

#### 5.2.1 大小文件限流闸门（`SizeAwareConversionGate`）

PDF 转换器实例重且非线程安全，大文件并发会撑爆内存。闸门提供读写锁语义：

- 小文件（< `threshold`）：最多 `small_capacity` 路并发（读者）
- 大文件（≥ `threshold`）：独占（写者），且它排队时阻止新小文件入场（防饿死）

**`acquire()` 返回许可令牌，`release(permit)` 凭据归还**——这一点是硬约束，不是风格问题：

旧实现 `release(size)` 用**当时的** `threshold` 重新判定 `size` 属于大/小。而 `RAGEngine.__init__`
每次构造都会 `configure()` 热改阈值（同步期间重建引擎、改配置都会命中），于是「按小文件入场、
期间阈值被调小」的请求会在 release 时走进写者分支 —— `_writing = False`（本来就是 False，
空操作），而 `_readers` 永远不会被减回来。`_readers` 单调增长后，写者的等待条件
`while self._readers > 0` 永不满足 ⇒ **所有后续大文件转换永久阻塞**，且没有任何超时与日志，
表现为「同步莫名卡住」。

`release()` 另外校验重复归还（`_writing` 为 False 时的写者 release、`_readers <= 0` 时的读者
release 都记日志并忽略）——`_readers` 变负会直接破坏「大文件独占」：写者条件在仍有真实读者
时也会通过。

### 5.2.2 OCR 引擎选择与预处理分流

「图 → 文字」的唯一入口是 `parsers.ocr_recognize_array()`，PDF 图片页与扫描版 epub 图片共用
它，保证两条通路的预处理与引擎策略完全一致：

1. 先走 **ocrmac（Apple Vision）**：`framework="vision"`、`recognition_level="accurate"`、
   `language_preference=["zh-Hans", "en-US"]`（**必须显式带 `zh-Hans`**：留空时 Vision 会把
   中文识别成西里尔乱码）；
2. 本页 ocrmac 未装 / 抛异常 / 没识别到文字 → 该页改用 **RapidOCR** 补充；
3. **按页回退，不是全局切换**：下一页依旧优先 ocrmac。

预处理必须按引擎分流，不能共用一张图：

| 引擎 | 输入 | 原因 |
|------|------|------|
| ocrmac | 灰度（**不二值化**） | Otsu 二值化会抹掉 Vision 依赖的抗锯齿笔画与灰度过渡 → ocrmac 读不出字 |
| RapidOCR | 二值化 | 其 det/rec 在纯黑白样本上训练，二值化更利检测 |

上游（PDF 的 `_ocr_preprocess`、epub 的 `ocr_epub_images`）只负责把图解码成**灰度原图**，
完整预处理由 `ocr_recognize_array` 内部分别施加，避免重复处理与二值化污染 ocrmac 输入。

ocrmac 经 pyobjc 调用 `VNRecognizeTextRequest`，每次识别产生的 ObjC 对象靠 autorelease pool
回收；worker 子线程没有主线程那种隐式排空，故模块加载时全局 monkeypatch `ocrmac.OCR`，
**只给 `recognize()` 套池**（构造必须留在池外：`return inst` 位于 `with` 内会让池在识别发生
前就排空，留下悬垂引用）。

RapidOCR 单例的并发约定：取引擎与释放都**在同一把 `_OCR_SEMAPHORE` 下**进行
（`_ocr_image_cached` 在信号量内取引擎，`release_ocr_engine()` 先抢信号量再释放）。否则会出现
两代 ~500MB 引擎并存，或释放掉 worker 正握着的引擎（原生段错误）。取锁顺序恒为
「信号量 → `_OCR_ENGINE_LOCK`」，不会出现 AB-BA 死锁。

### 5.3 阻塞对话协议（confirm / ask_user）

```
Worker 线程                         UI 主线程
─────────                           ─────────
callbacks.confirm(msg)
  ├─ _confirm_event.clear()
  ├─ bridge.confirm_request.emit(msg)  ──→  _on_confirm_request(msg)
  └─ _confirm_event.wait(timeout=600)      ├─ QMessageBox.question(...)
                                            │  (UI 阻塞等用户点击)
                                            └─ set_confirm_result(reply == Yes)
                                                  ├─ _confirm_result = val
                                                  └─ _confirm_event.set()
  ← 被 set 唤醒
  return _confirm_result
```

- 超时 600s，避免 worker 永久卡死。
- `cancel()` 同时 set 两个 Event，让阻塞中的 `confirm`/`ask_user` 立即返回。
- **默认拒绝**：`_confirm_result` 初值为 `False`、`_ask_result` 初值为 `None`，且 `Event.wait()` 的返回值被检查——超时或事件丢失时返回「拒绝 / 无回答」，而不是沿用上一次的结果。`shell_run` / `code_run` 等高风险操作绝不能因为对话框没回话而被默认放行。
- `BridgeCallbacks.reset()` 在每轮 `_on_send` 前复位 `_cancelled` / 结果 / Event，避免「终止对话」后残留状态污染下一轮。

### 5.4 信号命名陷阱

**所有** `QThread` 子类的自定义完成信号都不能命名为 `finished` —— 会遮盖 QThread 内置的 `finished` 信号，导致 `deleteLater` 在 `run()` **内部**触发（在线程仍在运行时销毁它），而真正的 `finished`（run 返回后）反倒没有监听者。

- `SyncKnowledgeWorker`：`sync_finished` / `sync_failed` / `sync_progress`（正确）。
- `InstallDepsWorker`：原为 `finished = pyqtSignal(object)`（**错误**），已改为 `deps_finished`；`deleteLater` 改挂到内置 `finished`。
- 另外，`MainWindow._is_worker_running()` 包装 `isRunning()` 并吞掉 `RuntimeError`——`deleteLater` 执行后 QThread 的 C++ 对象已被销毁，直接调 `isRunning()` 会抛「wrapped C/C++ object has been deleted」。

### 5.5 技能建议的延迟显示

`on_skill_suggested` 在 agent run 期间到达，但**不在 streaming 过程中弹模态对话框**（会阻塞 UI 事件循环，导致 content/reasoning chunk 无法渲染）。技能建议被缓存到 `_pending_skill`，在 `_on_finished` 之后（worker 线程已 join）才显示对话框。

### 6.2 显式释放的必要性

Python GC 无法及时回收以下 C++ 资源：
- **ONNX Runtime InferenceSession**（~137MB embedding + ~500MB reranker）：引用计数 + 循环 GC 才会触发析构，期间内存不释放。Embedding 模型通过 `get_or_create_embedding_function()` 进程级单例共享（RAG + 知识图谱共用），避免加载两份；共享时不 `session.release()`，仅 `VectorStore.close()` 时解除引用。
- **LongTermMemory 单例**：缓存在 `ToolRegistry._long_memory_instance` 上，`shutdown()` 时 `lm.close()` 释放 LanceDB 连接；不调用则会随 `_rebuild_agent()` 泄漏。
- **LanceDB 连接**：持有文件句柄和 mmap。
- **MCP 子进程**：不 stop 会变成僵尸进程。

因此 `VectorStore.close()` 显式：
1. 调用 `InferenceSession.release()` 立即回收 C++ 堆。
2. `model.cpu()` 把 PyTorch tensor 移出 GPU。
3. 置 None 让 Python 引用消失。

### 6.3 `_rebuild_agent` 的清理顺序

应用配置时重建 agent：
1. `old_agent.tools.shutdown()` — 停 MCP 子进程、关 RAGEngine。
2. `old_llm.close()` — 关 httpx 连接。
3. 创建新 `LLMClient` + `Agent`。

**运行期间禁止重建**：`_on_apply_config` 检查 `_busy`，若 agent 正在运行则弹窗拒绝（否则会销毁正在使用的 tools/httpx）。

### 6.4 窗口关闭清理（`closeEvent`）

**第一步必做**：`self._bridge.blockSignals(True)`。`AgentWorker.run()` 是**直接**调
`self._callbacks.bridge.*.emit()`，sender 是 Bridge 而不是 worker —— 后面
`_shutdown_worker()` 里的 `worker.blockSignals(True)` 挡不住它们。若屏蔽动作放在释放
agent/llm 之后，就会在 worker 仍在跑时跨线程 close 掉它正在使用的对象（UAF）。

随后停掉**所有**定时器：`_log_poll_timer`、`_plan_poll_timer`、`_stream_flush_timer`、
`_reason_flush_timer`（后两个是流式刷 UI 的 singleShot 100ms，漏停会在关窗后 fire 打到
已释放的 `chat_view`/`think_view`）。

对每个 QThread worker（含此前被完全遗漏的 `LoadModelWorker`）：
1. `blockSignals(True)` — 屏蔽业务信号，让 emit 变 no-op（**不能用通配 `disconnect()`**：
   它会把 `finished → deleteLater` 一起断掉，见 6.4.3）。
2. 协作式 `cancel()`（若支持）。
3. `wait(timeout)` — 等 run 返回。
4. 仍存活则 `terminate()`（最后手段，不安全）；**`wait()` 返回 False 时必须保留引用**，
   宁可让 Python 侧泄漏一个对象，也不能让进程 abort。

**关键约束：只在线程确认停止后才关引擎**。`RAGEngine.close()` 会先 join 内部那批 ingest
worker 线程（默认 deadline **600s**），而 `QThread.terminate()` 杀不掉它们——它们卡在
docling 的原生线程池里，没有取消点。旧实现无条件调用，于是「同步进行中点关闭窗口」会在这行
**同步阻塞最多 10 分钟**：窗口不消失、事件循环不转，表现为彻底卡死。现在
`_shutdown_worker()` 返回 False 时直接跳过 `close()`（并记 warning），宁可让引擎随进程退出
回收，也绝不在主线程 join 第三方原生线程。

之后：
- `agent.tools.shutdown()` — MCP 子进程 + RAGEngine。
- `agent.close()` — 释放事实抽取专用的独立 `LLMClient`（独立 httpx 连接池）。`_rebuild_agent()` 会做这一步，但**直接关闭窗口不走那条路径**，原先会泄漏该连接池。
- `llm.close()` — httpx 连接。

### 6.4.3 QThread 保活登记表（`_worker_refs`）

**问题**：历史上多次出现 `QThread: Destroyed while thread '' is still running` → Qt
`qFatal` → 进程直接 abort（**没有 Python traceback**）。

**根因**：业务完成信号（`deps_finished` / `sync_finished` / `sync_failed` /
`dedup_finished` / `fetched`）都是在 `run()` **内部** emit 的，emit 与线程真正结束之间
还有一段窗口（Qt 要先 `emit finished`、清理 QThreadStorage、最后才 `running = false`）。
而对应的槽第一句往往是 `self._xxx_worker = None`——窗口内最后一个强引用消失 → Python 包装器
析构 → C++ `QThread` 被删 → Qt 看到 `isRunning()` → qFatal。少数路径再叠加
`finished → deleteLater`（queued 的 DeferredDelete）与**模态框**（嵌套事件循环会立刻派发
队列里挂起的删除事件）就会稳定命中。

**对策**：引用生命周期与业务状态解耦。

- 每个 worker 创建后立刻 `self._retain_worker(worker)` 登记进 `self._worker_refs`；
- 该方法连接的 `finished` 兜底槽先 `wait(2000)` 确认线程真的终止，才从表里移除；
- 业务槽照常置 `None`（那是 UI 状态语义，用于「还能不能再起新的」判断），但**不再承担保活职责**。

原来的 `worker.finished.connect(worker.deleteLater)` 全部替换为这套保活释放（含常驻的
`AgentWorker`）。terminate 后仍未能 join 的极端情况会保留登记并记 warning——泄漏一个对象
远好过进程 abort。

### 6.4.1 子进程与进程组

`shell_run` 和 MCP 都通过 `start_new_session=True` 让子进程自成进程组：

- **`shell_run`**：`shell=True` 会 spawn `sh -c …`，再 fork 出真实命令。只杀顶层 PID 会留下孙进程（后台服务、`pip`、`sleep`）成为孤儿。超时后用 `os.killpg(os.getpgid(pid), SIGTERM)`，3s 宽限后 `SIGKILL`，并关闭管道。
- **MCP**：`npx` 之类包装进程会再拉起真正的 server；`stop()` 同样用 `killpg` 回收整棵树。清理条件以 `_process` 为准（**不是** `_running`）——读线程的 `finally` 会在 server 自行退出时把 `_running` 置 False，若 `stop()` 据此提前 return，就没人 `wait()` 回收僵尸进程。

### 6.4.2 `_JsonStore` 的 atexit 泄漏

`atexit` 内部持有回调的强引用。旧实现在每个 `_JsonStore.__init__` 里 `atexit.register(...)` 且从不 `unregister`，于是每创建一个 store（LongTermMemory 重建、切换 workspace…）就永久新增一条回调及其闭包，进程生命周期内单调增长。

改为：模块级只注册**一个**全局回调 `_flush_all_stores`，遍历一个 `weakref.WeakSet` 中仍存活的 store。store 被 GC 后自动从 WeakSet 消失，回调数量恒为 1，且不会阻止 store 被回收。

### 6.5 RAG 资源竞态与解决

**问题**：`SyncKnowledgeWorker` 写完数据后，agent 的 `RAGEngine` 持有 stale 表句柄，看不到新数据。

**解决**：
- `SyncKnowledgeWorker.run()` 在 `finally` 中 `engine.close()` 释放 worker 侧资源后，才 `emit sync_finished`。
- UI 收到 `sync_finished` 后调用 `agent.tools.reload_rag()`，触发 `RAGEngine.reload()` 丢弃表句柄，下次操作重新打开。

### 6.6 日志控件并发崩溃与解决

**问题**：同步期间，`QSignalLogHandler` 的 queued signal 和 QTimer 轮询的 `appendPlainText` 同时操作 `log_view`，导致 PyQt6 内部断言失败调用 `abort()` 崩溃。

**解决**：
- `QSignalLogHandler._sync_active` 标志：同步开始时设为 `True`，`emit()` 中跳过 RAG 模块日志（`_RAG_LOG_PREFIXES` 匹配），避免与 QTimer 轮询竞争。
- 同步结束后恢复为 `False`，`QSignalLogHandler` 重新接管 RAG 日志。
- `_log_buffer` 用 `threading.Lock` 保护，确保多 worker 线程写入与主线程消费的原子性。

## 7. 错误处理

### 7.1 错误传播路径

```
工具层错误
  ├─ Tool.run() 抛异常 → ToolRegistry.execute 捕获 → ToolResult(False, error)
  └─ ToolResult 通过 on_tool_end 回调 → UI 显示，并写入 history 作为 tool message

Agent 层错误
  ├─ LLM stream 异常:
  │   ├─ context_length_exceeded → 被动收缩重试（最多 3 次）
  │   └─ 其他 → on_error + on_finished, 退出 run()
  ├─ parse_args 失败 → 报错给模型（写入 history），继续下一轮
  └─ 达到 max_iterations → on_finished, 返回当前 final_content

UI 层错误
  ├─ _rebuild_agent 失败 → on_error 弹窗
  ├─ sync 失败 → sync_failed 信号 → QMessageBox.critical
  └─ worker 异常 → bridge.error 信号 → _on_error 显示

RAG 层错误
  ├─ 单文件 extract 失败 → 记录到 stats["errors"], 跳过该文件
  ├─ 单文件 clean/chunk 失败 → 记录 + 跳过
  ├─ VectorStore add 批次失败 → 记录, 单批失败不中断（连续 ≥3 批才中断）
  └─ manifest 更新失败 → 警告日志, 不影响已写入的向量

MCP 层错误
  ├─ 命令不存在 → MCPError, ToolRegistry 跳过该 server
  ├─ 请求超时 → MCPError
  ├─ 子进程崩溃 → reader 线程退出, pending 请求回填错误响应
  └─ JSON 解析失败 → 警告日志, 跳过该行
```

### 7.2 防御性设计

- **JSON 持久化**：所有 `_JsonStore` 加载时 `try/except (OSError, json.JSONDecodeError)`，损坏文件回退到 `{}`。
- **类型防御**：`LongTermMemory` / `GraphMemoryStore` / `SkillManager` 加载后 `isinstance` 检查，None/损坏数据重置为空结构。
- **config 迁移**：`_migrate()` 把过期的 embedding 模型名（含非量化→量化升级）/ 过小的 `max_tokens` 自动升级到当前默认。
- **记忆迁移**：`LongTermMemory.__init__` 首次加载时自动将旧扁平事实列表迁移到知识图谱。
- **事实抽取容错**：`extract_facts_via_llm` 容忍 markdown 围栏、JSON 解析失败、LLM 异常，任何错误返回空图谱。
- **Embedding 单例共享**：`get_or_create_embedding_function()` 进程级单例，`_EF_SINGLETONS_LOCK` 保护并发初始化。`VectorStore.close()` 检查 `is_shared`，共享时不 `session.release()`（避免破坏其他调用方）。
- **LongTermMemory 单例**：`_get_long_memory(registry, config)` 缓存在 `ToolRegistry` 上，避免每次 tool 调用创建新实例泄漏 ONNX 模型。`shutdown()` 释放后置 None。
- **空操作回退**：`on_context_shrunk` 等回调用 `try/except` 包裹，避免 UI 异常影响 agent 循环。
- **悬挂消息修复**：`_trim_history` 和 `_shrink_context` 都确保 history 不以 `tool` 消息开头。

#### 8.2.1 配置窗口两分区与本地模型注册表（#140）

配置窗口（`ConfigWindow`）内部分两个 `QGroupBox`：

| 分区 | 行 | 说明 |
| --- | --- | --- |
| **Agent 模型配置** | 主模型模式（本地 / OpenAI 兼容接口，单选） | 顶层二选一，控制下面两块面板的可见性 |
| | 本地模式：主模型两行 + 辅助模型两行 | 行 1 = 模型类型（MLX-LM / MLX-VLM / ONNX / GGUF）+ 本地路径 + 选择；行 2 = context / Temp / top_p / min_p / top_k / repeat-penalty / 超时 + **加载模型** + **卸载** |

- **`llama_cpp` 一律在 UI 上显示为 `GGUF`**：下拉框用 `itemData` 存真实配置值（`_combo_backend_value` / `_select_combo_backend`），显示名面向用户。Embedding 下拉因此补上了 GGUF 项。
- **采样参数两套控件同名不同前缀**（`temp_edit` / `aux_temp_edit`）：`_add_sampling_row` 按 `prefix` 生成控件，`_gather_sampling_from_widgets` / `_apply_sampling_to_widgets` 按同一 `prefix` 读写 config，校验规则只有一份实现，不会两套阈值各自漂移。

**本地模型注册表**（`MainWindow._llm` / `_aux_llm` + 签名）：

- `_model_signature(role)` = `(模式, 后端类型, 路径)`，记录「这个后端对象是用哪份配置建出来的」。
- `_ensure_main_llm()` / `_ensure_aux_llm()`：签名相同就**复用**已有后端（权重保持热），不同才 close 旧的、建新的。`_rebuild_agent` 不再无条件 close + create——否则每次「应用配置」都要重新读数 GB 权重。
- **加载模型**：`LoadModelWorker`（QThread）里 `create_*_backend` + `_ensure_loaded()`，完成后由 `_on_model_loaded` 装到注册表并直接赋给 `agent.llm` / `agent.aux_llm`。加载期间配置变更（签名不符）则丢弃结果，避免装错模型。
- **卸载**：close 旧后端，再给 agent 换一个全新的懒加载后端——不能直接 close 了事，否则下一轮对话会撞上「本地模型后端已关闭」。
- **启动默认加载**（`_autoload_default_models`）：后台加载默认主/辅模型，`BASE_AGENT_SKIP_MODEL_AUTOLOAD=1` 可跳过（测试用，否则套件会真的读数 GB 权重）。自动加载失败只记日志不弹窗。
- 辅助模型是**可选增强**：路径不存在或运行时缺失时 `_rebuild_agent` 单独兜异常置 None，摘要自动回退主模型，不会把 agent 拖垮。

**辅助模型采样参数必须是实时视图**（`_AuxConfigView`）：本地后端通过 `getattr(self.config, "top_p")` 这类标准名读参数，辅助模型要用 `aux_*` 里自己那一套。视图在每次属性访问时回到源 config 现读——**不能用快照**，否则用户在配置窗口改完 Temp / context 再点「应用配置」，快照里的值还是旧的，参数看起来没生效。

**辅助模型的用途**：`Agent._summarize_via_llm`（上下文收缩时的摘要）优先走 `aux_llm`，失败自动回退主模型。摘要是轻量子任务，用小模型更快，也不占主模型的推理队列。

**旧配置迁移**：`llm_mode` 是后加字段，`AgentConfig.load` 在检测到该键缺失时按 `llm_backend` 反推模式——不能直接用 dataclass 默认的 `local`，否则会把一个一直用 OpenAI 接口的老用户静默切到本地 MLX。

## 11. 缺陷修复记录（本轮全量复查）

按影响面排序。每条均附根因与修复方式，便于回归定位。

### 11.1 致命：首次知识库同步永久卡死（死锁）

**现象**：全新安装、第一次点「同步知识」时，同步永远停在「同步中」，日志不再刷新。

**根因**：`VectorStore.upsert_document()` 先 `with self._documents_lock:`，再调用 `_ensure_documents_table()`；后者在 `_documents_table is None`（documents 表还没建）时再次 `with self._documents_lock:` —— 普通 `Lock` 不可重入，**自锁死**。ingest worker 卡在 `upsert_document`，主线程卡在 `q.get()`，双方无限等待。
之所以不是每次都触发：`_ensure_initialized()` 会顺手打开已存在的 documents 表，只有"表还不存在"这一条路径会死。

**修复**：`_documents_lock` 改为 `RLock`；并把建表逻辑拆成 `_ensure_documents_table_locked()`（假定已持锁），`upsert_document` / `delete_document` 在锁内直接调用它，不再嵌套 acquire。

### 11.2 `InstallDepsWorker.finished` 遮盖 `QThread.finished`

自定义 `finished = pyqtSignal(object)` 遮盖了内置信号，导致 `deleteLater` 在 `run()` 内部（还在运行时）被触发销毁线程；且 `_deps_worker.isRunning()` 可能抛 RuntimeError。已改名为 `deps_finished`，`deleteLater` 改挂内置 `finished`。

### 11.3 确认弹窗超时即默认放行

`Event.wait()` 返回值被丢弃，`_confirm_result` 初值为 `True`。对话框因任何原因没有回话时，`shell_run` / `code_run` 会被自动放行。改为初值 `False` + 检查 `wait()` 返回值；`ask_user` 同理返回 `None`，并新增 `reset()` 防止跨轮残留。

### 11.4 `skill_load` 任意文件读取（路径穿越）

`entry` 来自模型且未校验：`os.path.join(abs_dir, entry)` 在 `entry` 为绝对路径时直接丢弃 `abs_dir`，`../../` 又能逃出技能目录 —— 合起来等于允许读取磁盘任意文件。修复：入口名显式拒绝绝对路径与含 `..` 的分段；解析后再用 `realpath` 前缀校验；拒绝时**直接报错**，不允许回退到别的文件把非法请求伪装成成功。
同时修复了老技能（`skill.json` 声明 `entry: prompt.md`）用默认 `SKILL.md` 永远读不到内容的问题。

### 11.5 语义切片无视注入的 embedding function

`chunk_documents()` 从不把 `embedding_function` 往下传，`semantic_chunker._shared_embedding_function()` 因此总是去加载共享的本地 ONNX 模型：注入了自定义 EF（测试 `fake_ef`、未来的远端 embedding）也无效，离线环境还会卡在模型下载上。修复：`chunk_documents` → `_chunk_with_hybrid_fallback` → `hybrid_chunk_text` / `semantic_chunk_text` 全链路透传；`RAGEngine` 传入 `self._custom_ef`。
另外 `_shared_ef_resolved` 原在加载**前**置位，首次失败会被永久缓存，之后即使网络恢复也不再重试；改为只在成功时置位，并加锁避免并发重复加载。

### 11.6 切片文本包含原文中不存在的内容

两处拼接凭空造字符，导致 chunk 文本不是原文的连续子串（模型会看到源文件里没有的内容）：

- `semantic_chunker._tail_by_tokens()`：用 `re.split` 拆句后 `"".join` 拼回，分隔符里的 `\s*` / `\n` 被丢弃。改为在原文中定位句末边界后**直接切片**。
- `_merge_to_target_size()` / `_apply_overlap()`：硬编码 `"\n\n"` 作为连接符。改为 `_gap_between(source, left, right)` 取出源码里两片段之间**真实的间隔**。

### 11.7 docling 转换器：锁创建竞态 + `convert()` 完全无锁

`_converter_lock` 惰性创建（`if _converter_lock is None: ...`）是典型的 check-then-act 竞态，两个线程会各建一把锁、各建一个 `DocumentConverter`（数百 MB ×2）；而真正重入的 `converter.convert()` 却**完全没有加锁**，4 个 worker 并发调用未声明线程安全的转换器。修复：锁在模块导入时创建；`convert()` 用同一把锁串行化；新增 `release_converter()` 并在 `RAGEngine.close()` 调用（docling 模型不再常驻）。

### 11.8 `shell_run` 超时留下孤儿进程 + 输出无上限

`subprocess.run(capture_output=True)` 只 SIGKILL 顶层 `sh`，孙进程存活并继续持有管道；`capture_output` 全量读入内存，一条 `cat 大日志` 就能打满内存。改为 `Popen(start_new_session=True)` + 线程流式读取 + 进程组 SIGTERM/SIGKILL + 输出上限 200KB（超过则截断并标注）。

### 11.9 MCP `stop()` 留下僵尸进程

`stop()` 以 `not self._running` 为提前返回条件，而读线程在服务自行退出时会把 `_running` 置 False —— 这条路径跳过了 `terminate()`/`wait()`，子进程永远无人回收；若服务仍存活（仅 stdout 关闭）则成孤儿。修复：以 `_process` 为清理条件，`_running` 只作循环标志；加 `start_new_session=True` 并用 `killpg` 回收整棵树；关闭 stdin/stdout/stderr 三条管道（原先每次 rebuild 泄漏 fd）。
另外 `_read_loop` 对**迟到响应**（对应 `_call()` 已超时）无条件写入 `_results`，这些条目无人 pop，会永久驻留；改为丢弃。

### 11.10 配置：损坏即无法启动 / 静默篡改用户设置 / 非原子写

- `load()` 直接 `json.load`，写崩的 config.json 会让程序起不来 → 捕获异常后备份为 `.corrupt` 并用默认配置启动；同时对数值字段做类型强制（手工编辑常写成 `"32768"`）。
- `_migrate()` 把任何 `< 8192` 的 `max_tokens` 改成 32768，用户为本地 4K 模型显式设置的 4096/2048 每次启动都被改回 → 只在值等于旧默认 4096 时才迁移。
- `save()` 直接 `open(path,"w")`，写一半崩溃会留下截断的 JSON → 改为临时文件 + `fsync` + `os.replace` 原子替换。

### 11.11 技能索引：目录不存在时每次查询都写盘 + mtime 失效 + 锁外遍历

- `scan()` 在目录不存在分支只 `_save()` 不更新 `_last_scan`，导致 `_should_scan()` 恒为真：每次 `search()` 都 `makedirs` + 重写 `_index.json`。
- `_dir_mtime()` 只 stat 子目录，改写 `skill.json`/`prompt.md` 不改变目录 mtime，索引最迟 300s 才更新 → 现在同时 stat 目录本身与各 `skill.json`。
- `search()` 在 `scan()` 后不加锁遍历 `self._index` → 改为锁内取快照。
- `_load()` 的 `except` 未覆盖 `TypeError/AttributeError`（索引文件根不是 dict 时）→ 补全异常类型并校验结构。

### 11.12 `skill_retriever`：先删表后探测 → embedding 失败即丢索引

`build()` 先 `drop_table` 再探测 embedding 维度，一旦模型未下载/网络故障，已有可用索引已经被删掉。改为**先探测维度，成功后再删表重建**。
另外 `sync()` 用 `to_arrow().to_pylist()` 把含两条 768 维向量的整表读成 Python 对象（数千技能 ≈ 百万级 float），改为 `select(["dir","fingerprint"])` 只取需要的两列；`dir` 拼进 SQL 字面量前做 `''` 转义（目录名含单引号会让过滤表达式语法错误）；`close()` 真正调用 `db.close()`；扫描器 `_dir_mtime()` 只 stat 目录与 `SKILL.md`（原来 stat 每个文件，且每次查询走两遍全树）；BM25-only 候选的相似度查询只算一次 query 向量后复用。

### 11.13 `skills.py`：损坏记录拖垮整轮 + 请求表无界增长

`Skill(**s)` 与 `s["name"]` 遇到非 dict / 缺字段记录会抛 `TypeError`/`KeyError`，连带 `match()` 与 `record_request()` 一起失败 → 读取时逐条校验并跳过坏记录。
`requests` 计数表只增不删，长期使用的 `skills.json` 无界膨胀 → 超过 500 条时淘汰最旧的一半。停用词集合提到模块级（原来每轮对话重建）。

### 11.17 工具层遗留限制根治（第四轮）

上一轮（§11.16）标记为「已知限制」的两个问题，本轮一并解决：

**`execute()` 签名级参数预检**（`base.py`）

旧实现靠捕获 `run()` 抛出的 `TypeError` 判定「参数无效」——但 `TypeError` 同时也是工具内部 bug 的常见形态（`len(42)`、对 None 做运算等）。两者混在一起时，工具内部出错会被报成 "Invalid arguments"，模型据此反复重试同样的调用，永远意识不到是工具坏了。

修复：调用前先用 `inspect.signature(tool.run).bind(**args)` 做签名预检——
- 预检失败（缺参/多参/非 dict）→ `Invalid arguments for <name>`，模型可修正调用；
- 预检通过后 `run()` 再抛 `TypeError` → 明确报告 `<name> failed internally (not an argument problem)` 并 `logger.exception` 留痕。

**`code_run` 的 stdout 恢复权全部移交主线程**（`code_run.py`）

旧实现 worker 在自己的 `finally` 里恢复 `sys.stdout/sys.stderr`。正常路径下主线程 join 后也会恢复，两者冗余；但超时泄漏的线程会在**未来任意时刻**退出并触发它的 finally——把 stdout 恢复成「它启动时的值」。若此时恰好有下一次 `code_run` 在执行（已换上自己的 StringIO），那次执行的输出会被整个吞掉。

修复：worker 只负责切换（`os.chdir` + 替换 stdout/stderr），**不做任何恢复**；主线程在 join 后无条件统一恢复。这样泄漏线程退出时只往自己的 StringIO 写，不再触碰任何全局状态，与前一次超时泄漏并发的后续 `code_run` 是安全的。

两个行为均有回归测试覆盖（`test_execute_distinguishes_internal_typeerror`、`test_code_run_leaked_thread_does_not_hijack_stdout`）。

### 11.18 第五轮：pytest-qt 环境补齐 + `_JsonStore` reload 数据丢失

**环境**：PyPI 主站与清华镜像对本机不可达（403/超时），改用阿里云镜像装上 `pytest-qt`——`test_bridge.py` / `test_integration.py` / `test_ui_flow.py` 三个 UI 测试文件得以首次在本机完整执行。

**`_JsonStore.reload()` 丢弃防抖窗口内的未落盘写入**（`memory.py`，真实数据丢失）

`_JsonStore` 采用防抖写入：0.5s 内多次 `set()` 只在最后一次落盘（`set()` → `_dirty=True` + 间隔够长才 `_save()`）。而 `reload()` 直接 `_load()` 用磁盘内容**整体覆盖** `_data`——若 reload 距上一次 `set()` 不足 0.5s，那次 set 的内容**还没写到磁盘**，就被磁盘旧数据覆盖，静默丢失。

触发链路（用户可感知）：`main_window._show_pending_skill_dialog()` 在 `create_skill()` 保存技能后立刻调用 `skills.reload()` 防止重复建议——但本轮对话的 `record_request()` 写入若发生在 0.5s 内（快速响应/缓存命中时），`create_skill` 的写入仍在防抖窗口里，`reload()` 一执行，**用户刚固化的技能直接丢失**，且无任何报错。

修复：`reload()` 在 `_load()` 前先把脏数据强制写回（`if self._dirty: self._save()`）。语义上 reload 的前提是「我的内存状态已安全持久化，需要吸收外部修改」，旧实现违背了这一前提。

发现过程值得一提：该问题先以「测试顺序相关的偶发失败」暴露——`test_skill_suggestion_cached_during_run_shown_after_finish` 单独跑必过、与其它 UI 测试同跑必挂。通过给 `_JsonStore._save/_load/reload` 打桩对比两种场景的存储事件序列，确认隔离运行时防抖窗口恰好擦肩而过（时序侥幸），组合运行时窗口命中。**测试通过不等于没有 bug——这次是时序侥幸掩盖了数据丢失。**

回归测试：`test_json_store_reload_flushes_pending_writes`（内存与磁盘双重断言）。

### 11.19 第六轮：全链路复查（RAG 一致性 / UI 生命周期 / 并发 / Prompt 效率）

四个子代理并行审查 `agent.py`+`llm_client.py`+`config.py`、`rag/*`、`tools/*`+`ui/*`、`memory.py`+`graph_memory.py`+`skills.py`+`skill_*`，并专项审查全仓 prompt。以下按影响面排序，均与 README「近期修复」第 45–65 条对应。

#### 11.19.1 BM25 索引一致性三处断裂（混合检索静默退化）

| 位置 | 问题 | 后果 |
|---|---|---|
| `add_streaming` 单批提前 `return` | 跳过末尾的 FTS 重建 | 小知识库（<20 切片）同步后 BM25 查不到新数据，混合检索退化成纯向量，**无任何报错** |
| `delete_by_source` | 删向量后不置 `_fts_ready = False` | 已删除文档的 term 仍在倒排索引里，被关键词检索召回并交给 LLM |
| `reload()` | 只重置 `_table` | 同步后 `rag_outline` 读到旧 digest、BM25 看不到新切片 |

修复：提前出口同样重建索引；删除后失效标记；`reload()` 一并重置 documents 表/缓存/FTS 两个标志。

设计要点：这三条都不会抛异常、也不会让测试变红——**失效是静默的**。因此修复时统一在「数据变更」与「句柄刷新」两个语义点强制失效，而不是依赖调用方记得。

#### 11.19.2 documents 表存全文 Markdown（第三份冗余 + 无界内存）

`build_and_store_digest()` 把整篇 markdown 传给 `upsert_document`，而 `rag_outline` 只读 `digest`——**`markdown` 列零消费者**。语料因此在磁盘存 3 份（源文件、`rag/documents/*.md`、LanceDB 表），且 `_documents_cache` 全量载入后常驻进程（≈ 整个知识库字符量）。

修复：表内不再存全文，改存 `md_path`（指向已有缓存）；`_load_documents()` 按列读取并在写缓存前显式 `pop("markdown")` 兼容旧数据；`_ensure_documents_table_locked()` 建表时不再建该列。附带修复 M5（缓存读写未加锁导致「旧快照被写回」的竞态）——`_load_documents` 整体纳入 `_documents_lock`。

#### 11.19.3 UI 生命周期：`_fetch_worker` 从不置 None → 关闭窗口必崩

`FetchModelsWorker` 挂了 `deleteLater`，但 `_on_models_fetched` / `_on_fetch_failed` 都没清空 `self._fetch_worker`。此后 `closeEvent` 调 `isRunning()` 抛 `RuntimeError: wrapped C/C++ object has been deleted`；该异常从 `closeEvent`（虚函数重写）逃出，PyQt 5.5+ 默认 `qFatal()` → **进程 abort**。触发路径很普通：获取模型成功后关闭窗口。

修复：两个槽都清空引用；`closeEvent` 里 4 个 worker 与 `_on_stop_sync` 的两处判断**统一改用 `_is_worker_running()`**（该函数本就是为这个问题写的，之前有 6 处绕过它）。

#### 11.19.4 并发与阻塞

- **确认弹窗被抽取线程阻塞最长一个 LLM 请求**：`_get_extract_llm()` 无条件 `with self._fact_extract_lock`，而抽取线程在**整个 LLM 调用期间**持锁。修复：非阻塞 `acquire(blocking=False)`，取不到直接复用 `self.llm` 走本次调用——实现终于与「不延迟确认弹窗」的注释意图一致。
- **`_load_documents` 缓存读写无锁**：见 11.19.2。
- **`_get_skill_index` 完全无锁**：并发首次调用产生两个 `SkillIndex`（构造即全目录扫描 + 落盘）。修复：模块级锁 + 双重检查。
- **`GraphMemoryStore.close()` 只置 None 从不 close**：每次「应用配置」泄漏一个 LanceDB 连接。修复：显式 `close()` 并重置 `_vec_tried`（否则 close 后无法重新初始化）。

#### 11.19.5 功能正确性

- **`memory_search` 关键词兜底路径完全忽略 `top_k`**：未装 rag 可选依赖时（默认路径）一次宽泛查询会灌入全部 observation，与工具里其他地方的钳制自相矛盾。修复：`_keyword_search(query, top_k)` 生效。
- **技能分词 `\w+` 对中文失效**：`"提取pdf表格"` 成为单个 token，关键词 `pdf`/`提取` 永远不在集合里，中文技能检索恒为 0 分。修复：`_keywords_of()` 额外切出 CJK 整串 + 字符 bigram。
- **`usage` 字段为 `null` 时整轮崩溃**：`api_total = usage.get("total_tokens", 0)` 在网关返回 null 时得到 `None`，`None > 0` 抛 TypeError，且该段**不在 try 保护范围内** → 异常穿出 `run()`，回复丢失。修复：`usage.get(x) or 0` 归一（两处）。
- **工具层 RAG 引擎初始化在 try 之外**：知识库目录不可创建时，异常冒泡到 `ToolRegistry.__init__` → **文件/shell/web 等所有工具一起失效**。修复：整段包 try，失败仅跳过 RAG 工具。
- **`shell_run` 的 `timeout` 无钳制**（`code_run` 有）：传 99999 → 阻塞 27h 且无法被「终止对话」打断；传 0 → 立刻 kill。修复：钳制到 [1s, 600s]。
- **`web_scan` 流式失败 `except Exception: pass` 后静默重发**：真实超时会对同一 URL 再发一次完整请求（最坏 2×30s、重复流量），已读内容整段丢弃。修复：仅 `AttributeError`（替身无 `stream`）才回退，传输错误直接上抛。
- **`_reranker_state` 打分失败后停在 `"done"` 而模型为 None**：状态机失真。修复：同步置 `"failed"`。

#### 11.19.6 Prompt 效率与有效性

全仓 prompt 基线约 1,400–1,600 tok/轮。本轮改动：

**精简（约 −100 tok/轮）**：SYSTEM_PROMPT 删除模型已知的 function-calling 协议说明、`content`/`reasoning_content` 字段释义、以及可由前件推断的反例；摘要 prompt 合并重复条目；代码用途 prompt 压缩四重限定。

### 11.20 第七轮：遗留限制根治（沙箱 / MCP / manifest / 生命周期互斥）

本轮把前几轮列为「遗留」的四项结构性限制全部落地，并修掉新引入代码的同行评审问题。

#### 11.20.1 `code_run` 改为受限子进程沙箱

进程内 `exec` 有两个无法用工程手段修掉的问题：**线程杀不掉**（超时后死循环线程存活到进程退出）、**写路径拦不全**（只 patch `builtins.open` 时 `pathlib.Path.write_text` / `os.open` / `os.remove` / `shutil.*` 都能绕过）。

新方案：`python -c <bootstrap> <workspace> <sandbox_tmp> <cancel_file>` 起一个独立进程组的子进程，代码经 stdin 喂入。

- **可强杀**：超时先立取消标志文件（供协作式脚本 `_cancelled()` 退出），再 SIGTERM → SIGKILL `killpg` 整棵树。实测超时后无 100% CPU 残留进程。
- **防护覆盖面**：引导脚本在子进程里 patch `builtins.open` / `io.open`、`os.{open,remove,unlink,rmdir,mkdir,makedirs,rename,replace,truncate,link,symlink,chmod,utime}`、`pathlib.Path.{open,write_text,write_bytes,mkdir,rename,replace,unlink,rmdir,touch,symlink_to}`、`shutil.{copy,copy2,copyfile,move,rmtree,copytree}`。
- **目标路径校验**（同行评审发现的关键漏写）：`rename`/`replace`/`link`/`symlink` 的写副作用发生在**第二个参数**，只校验源等于没拦 —— 补上双向校验；`pathlib` 侧同步。
- **int fd 放行**：`subprocess` / `os.fdopen` 内部大量走这条路径，拦截会让 `subprocess.check_output` 这类合法调用失败。
- **临时目录**：每次执行 `mkdtemp` 独立目录（固定可预测路径有多实例劫持风险），`tempfile.tempdir` 与 `TMPDIR` 一并指向它；退出前 `rmtree` 清理。
- **兜底**：冻结包（PyInstaller）里 `sys.executable` 是 GUI 二进制 —— `_python_executable()` 在 PATH 中找同名解释器；找不到则回退原进程内路径。

**这仍不是安全边界**（`subprocess` 可逃逸、无 OS 级沙箱），确认弹窗依旧是实际防线；但相对进程内方案，超时可终止、写路径覆盖到 pathlib/os/shutil 层面。

#### 11.20.2 MCP 连接后台化 + 可重试

- 连接（握手 + `tools/list`）同步阻塞，一个起不来的 server 要等满 30s。原先在 `ToolRegistry.__init__` 里跑，而它在 UI 线程被 `_rebuild_agent()` 调用 → 配置 N 个 server 就是 30s×N 的界面冻结。
- 改为：构造时只创建 client（廉价）并起守护线程 `mcp-connect`；`_tools` 读写走 `_tools_lock`，读侧取快照。
- 工具被调用时尚未连上时 `MCPClient.ensure_started()` 现场拉起；失败时给出带上下文的错误。
- **握手失败可重试**：原先 `_start_locked` 的 except 调 `stop()`，而 `stop()` 会置 `_stopped` → 一次瞬时失败等于该 server 本进程内判死刑。拆出 `_teardown(stopped=False)`：收掉进程但不禁止重连。
- 重连前若发现旧进程仍存活（读线程可能只是因 stdout 关闭而退出），先 `_teardown` 再重建，避免孤儿。
- 代价：配置生效后的第一轮对话可能看不到 MCP 工具。

#### 11.20.3 manifest 跨进程锁 + 读改写合并

UI 同步与 agent 自动 ingest 各持一份内存快照，原 `_save_manifest` 是**全量覆盖写** → 后写者用旧快照抹掉前者刚写入的条目，「已同步」文件被判为「未同步」而全量重跑。

- `_ManifestLock`：`fcntl.flock`（跨进程）+ 进程内 `Lock`。**锁不可重入且用 TLS 计数**：flock 绑定在 open file description 上，同线程再 open 一次会与自己的 `LOCK_EX` 互斥；若配 RLock 就会自锁死。
- `_save_manifest(rag_dir, files, removed)`：持锁后重读磁盘 → `removed` 强制 pop → `files` 覆盖。用 `removed` 区分「我删的」（必须删）与「别人并发写的」（必须保留）。
- `RAGEngine.clear()` 删 manifest 也持锁，否则会被并发写**复活**（向量库空、记录满，检索永远返回空且不自愈）。

#### 11.20.4 `clear()`/`close()`/`reload()` 与在途操作互斥

`clear()` 会 `drop_table`、`close()` 会把 `_db` 置 None、`reload()` 会把 `_table` 置 None——与在途 `add`/`search` 并发会打到已删表或 `None` 连接。

- 在途计数 + 条件变量：`_store_op` 装饰器登记 15 个公开方法；`clear/close/reload` 先 `_drain_ops()`（有界等待，超时告警继续，不把 UI 卡死）。
- `_begin_op` **同时检查 `_closing`**：排空成功后到 `drop_table` 之间新来的操作也必须拒绝，否则只堵住一半。
- `clear()` 不能加 `@_store_op`（会自己等自己）；`close()` 排空后保持 `_closing=True`（实例永久不可用）。
- 关闭后调用任何方法抛明确 `RuntimeError`，不再是 `AttributeError`。

#### 11.20.5 Agent 回调隔离与抽取线程泄漏

- `on_token_speed`（流内）、`on_usage`、`on_token_speed`（收尾）、全部 `on_finished()` 原先是裸调用：任一抛异常 → `on_finished()` 永不执行 → **界面永久忙碌**；流内那个还会被外层 `except` 误报成「LLM 流错误」并丢掉本轮全部内容。统一改 `_safe_callback`。
- `is_cancelled()` 同样隔离：裸调用异常会穿出 `run()`，让已入历史的 `assistant(tool_calls)` 缺配对 tool 消息 → **下一轮 API 400**。
- `_get_extract_llm()` 取不到锁/构造失败时**不再退回 `self.llm`**（那正是它要避免的：守护线程与主线程共用 `httpx.Client`），返回 `None` 并放弃本次抽取。
- `Agent._closed` 标志：`close()` 后置位，抽取线程（不被 join）据此不再新建专用 client / LongTermMemory；`_get_long_memory` 检查 `registry._shutdown`，避免 `shutdown()` 之后重建 ~137MB ONNX 实例。

#### 11.20.6 UI 生命周期与主线程阻塞

- **`_on_send` 覆盖存活 worker**：只判 `_busy` 不够（`_on_finished` 在 join 超时时会保留 `self._worker` 并置 `_busy=False`）→ 再发送会丢掉运行中 QThread 的最后引用，Qt `qFatal` **进程静默退出**。增加 `_is_worker_running` 校验与同步期拒绝发送。
- **异步 join**：`worker.wait(2000)` 改为 300ms + `QTimer` 轮询重试，避免每轮结束最多冻结 2s。
- **`closeEvent` 通配 `disconnect()`** 会把 `finished→deleteLater` 一起断掉，且 `terminate()` 后无条件丢引用 → 同样的 abort。统一为 `_shutdown_worker()`：`blockSignals` + 保留 `finished→deleteLater` + **未确认结束则保留引用**。
- **重资源释放移出主线程**：`tools.shutdown()`（MCP join + 停子进程 + 释放 ~600MB 模型）改在后台线程执行。
- **互斥补齐**：「应用配置」与同步/依赖安装互不加锁（原只挡 agent 忙）；`_reset_sync_ui` 无条件解锁同步按钮改为 `not self._busy`。
- **同步临时 logging handler**：`terminate()` 时 `finally` 不执行 → handler 永久残留（闭包持有整个 worker）+ 日志重复；在 `QThread.finished` 槽无条件补摘，并恢复 `setLevel` 旧值。
- **流式渲染攒批**：每 chunk 一次文档重排改为 100ms 攒批 flush；只读视图 `setUndoRedoEnabled(False)`（数千次 `insertText` 会撑爆 undo 栈）。
- 确认/提问槽用 `try/except/finally` 保证 `set_confirm_result` 一定被调用（否则 worker 线程卡满 600s）。

### 11.23 重排序去 FlagEmbedding 化：统一到 fastembed ONNX 栈

#### 11.23.1 动机

旧实现用 `FlagEmbedding.FlagReranker` 加载 `bge-reranker-base` 做检索精排。这条依赖链问题集中：

- FlagEmbedding 连带安装 PyTorch（~2GB）与 transformers，且与 transformers 5.x 存在 API 断裂（XLMRobertaTokenizer 缺 `prepare_for_model`）；旧版 torch 与 numpy 2.x 不兼容还需要运行时探测（`tensor.numpy()` 试跑）。
- 模型文件 `pytorch_model.bin` ~1.1GB（fp32 全量）。
- 与嵌入链路（fastembed/ONNX）完全割裂，两套模型管理、两套下载逻辑。

而 fastembed 0.6+ 自带 `TextCrossEncoder`（ONNX cross-encoder），支持 bge-reranker 系列——嵌入与重排序可统一到同一条 fastembed / onnxruntime 依赖栈。

#### 11.23.2 模型选型：bge-reranker-v2-m3-int8

fastembed catalog 提供的 reranker 中，选官方 INT8 量化版 `BAAI/bge-reranker-v2-m3-int8`（HF 源 `onnx-community/bge-reranker-v2-m3-ONNX`，`onnx/model_int8.onnx`）：

| 候选 | 体积 | 说明 |
|---|---|---|
| bge-reranker-base（fp32 onnx）| ~1.1GB | 与旧版模型同源，但 ONNX 转换后体积不减 |
| **bge-reranker-v2-m3-int8** | **~570MB** | BGE-M3 基座（多语种，中文精排优于 base）+ 官方 INT8 量化 |
| bge-reranker-v2-m3（fp32）| ~2.3GB | 精度上限最高，体积过大 |
| ms-marco-MiniLM-* | ~90MB | 英文 ms-marco 训练，中文知识库场景不可用 |

INT8 权重在 CPU EP 上有原生 int8 算子加速；cross-encoder 输入是变长 (query, doc) 序列，attention 动态 shape 在 CoreML EP 上频繁 fallback，故 reranker 不启用 CoreML（与 OCR 策略相反）。

#### 11.23.3 实现要点

- **分数语义保持**：fastembed `rerank()` 返回模型原始 logit（全库无 sigmoid 处理），而旧 `FlagReranker.compute_score(normalize=True)` 返回 sigmoid 后的 [0,1]。`vector_store._logit_to_score()` 分段计算 sigmoid（避免 `exp` 溢出），下游 `min_similarity=0.7` 阈值过滤语义不变。
- **懒加载状态机保留**：`_reranker_state`（idle/loading/done/failed）+ RLock 串行化 + close() 后禁止复活 + 120s 后台加载超时，全部沿用；torch 兼容性探测段整体删除。
- **预下载幂等化**：`_download_reranker_model` 改为 `TextCrossEncoder(RERANK_MODEL_ID, lazy_load=True)`——只下载 catalog 文件、不创建 session；重复调用对已缓存模型秒回。
- **缓存判定迁移**：fastembed 经 `snapshot_download` 缓存（`<cache>/models--<org>--<name>/snapshots/<rev>/`），`_is_reranker_cached` 复用 `define_cache_dir` 定位缓存根，且只有 `model_int8.onnx` 真实存在才算已缓存（config/tokenizer 不算——中断下载的残留不该骗过预下载）。
- **deps 检查**：FlagEmbedding 的 missing_optional 检查删除，替换为 fastembed>=0.6 版本下限（低于则进 missing_required 自动升级）；fastembed 缺失/过旧时跳过 reranker 模型缺失检查（模型检查此时无意义）。
- **依赖瘦身**：pyproject 移除 FlagEmbedding + transformers，fastembed>=0.4 → >=0.6。运行时收益：省 ~2GB Python 包 + 权重从 1.1GB 降到 570MB。

旧配置里已存的 `bge-reranker-base` 仍被 fastembed 支持（fp32 onnx ~1.1GB）；后续 #107 的 `_migrate` 将该旧默认值统一升级到 INT8 版（见 §11.24.2）。

> **#131 补遗（配置转发断链修复）**：上述选型从未真正生效——两个真实调用点（`tools/base.py`、UI 同步线程）都不传 `rerank_model`，实际吃的是 engine.py 旧本地默认 `BAAI/bge-reranker-base`（fp32 ~1.04GB 非量化），`config.rag_rerank_model`（含 #107 迁移逻辑）是死代码。修复三处：① engine.py 默认值改引 `DEFAULT_RERANK_MODEL`；② 两个调用点显式转发 `config.rag_rerank_model`（配置恢复可覆盖）；③ `TextCrossEncoder` 显式传持久 `cache_dir`（fastembed 默认落系统临时目录，macOS 清理 → 重复下载，与 #121 同型）+ `providers=["CPUExecutionProvider"]` 锁死（与嵌入模型同款，不依赖 fastembed 默认行为）。

#### 11.25.1 工具层（#110，7 项）

- **memory 工具 observations 污染**：模型传字符串时 `for o in "部署在AWS上"` 逐字符入库，一次调用塞进几十条单字观察并触发同等数量嵌入。run() 入口归一化（字符串→单元素列表，元素过滤 None）。
- **file_modify old=""**：`"" in text` 恒真，`text.replace("", new)` 在每两个字符之间插入 new——一次调用静默损坏整个文件（无确认无备份）。空串直接拒绝。
- **_atomic_write 的 umask 翻转**：`os.umask(0)/os.umask(mask)` 是进程级副作用，翻转窗口内其他线程创建的文件拿到 0666。改为新建文件直接 `fchmod 0644`（不再读 umask）。
- **web_fetch SSRF 绕过**：只拦点分 IP 字面量，`http://2852039166/`（十进制）与 `0xA9FEA9FE`（十六进制）被 getaddrinfo 解析回 169.254.169.254——云元数据端点可被模型读取。检测层补 `int(host, 0)` 归一判断。
- **code_run 输出泵内存**：`TextIOWrapper.readline()` 在内部缓冲区累积整行才返回，「单行截断」防的是最终副本不是内存——一条 500MB 无换行 print 内存峰值就是 500MB。改 8192 分块读取自行按 `\n` 切行，行超限立即写截断标记并丢弃到行尾，峰值恒定。
- **MCP stdin 挂死**：`stdin.flush()` 无超时且持有 `_write_lock`——server 进程活着但不读 stdin、64KB 管道写满时 agent 线程永久卡死（无 watchdog）。改 `os.write + select` 带超时（15s）分块写，超时抛 MCPError 判定不健康；fd 不可用（测试替身）时回退文本写。

#### 11.25.2 RAG 层（#111/#112，7 项）

- **digest 孤儿行**：documents 表 doc_name 存相对路径、doc_id 是 md 缓存路径哈希，清理却按 basename/绝对路径删——子目录文件的行永远删不掉，rag_outline 持续列出已删文档。清理补 `delete_document(rel_path)`（doc_name 精确命中）。
- **digest 重刷双行**：ensure_digests 调 build_and_store_digest 漏传 md_path（变量就在作用域内）——upsert 落 hash(doc_name) 的新行，与 hash(md_path) 旧行并存，精确匹配永远命中旧行。补传。
- **删除失败吞异常**：delete_by_source 吞掉所有异常返回 0，engine 无条件 pop manifest——失败文件的向量永久残留且 FTS 重建会把它捞回来。改为失败抛出 + engine 侧失败保留 manifest 条目下次重试。
- **同步 TOCTOU**：rglob 扫描与 os.stat 之间文件消失（编辑器临时文件/云盘同步）会让整个 ingest 崩掉。per-file try/except 记入 errors。
- **旧版 Office 格式**：.doc/.xls/.ppt 之前路由给 python-docx/openpyxl/python-pptx——三者均只支持 OOXML，100% 失败且依赖白装。移出 SUPPORTED_EXTENSIONS/EXTENSION_DEPS，解析入口给出「另存为 OOXML」的明确提示。
- **MOBI 裸解析**：calibre 缺失时全量 read + decode + findall ≈3× 文件大小峰值。加 100MB 上限，超限提示安装 calibre。
- **chunker 伪造分隔符**：深层递归切片与外层 chunks 混列后统一用外层 sep 做重叠拼接——外层 sep 在相邻 sub_chunk 间不存在，产物非原文子串（semantic_chunker 已修同类，此路径未同步）。`_gap_between` 上移到 chunker.py 共用，merge 时定位原文真实间隔。

#### 11.25.4 agent 核心（#114，5 项）

- **backfill 死代码**：`_ensure_vectors` 的重试块位于早退 gate（`_vec_ready or _vec_tried`）之后——init 成功后每次调用都早退，日志承诺的「下次调用将重试」永远不可达；且 `_backfill_vectors` embed 失败静默 return 后调用方照样置 `_backfilled=True`。重试移到独立的非阻塞 `_retry_backfill`（独立 `_backfill_lock` 防并发），embed 失败显式抛出。
- **事实抽取类型污染**：extract_facts_via_llm 只查最外层是 dict——`"observations": "likes Python"` 被逐字符拆成单字事实永久污染图谱（去重无法自愈），entities 混非 dict 元素抛 AttributeError 炸整批。返回前统一收敛（list[dict] 过滤 + observations 归一 List[str]）。
- **delete_entity 持锁 IO**：`_deindex_observations`（LanceDB 删除事务 + table_names 文件探测，50-500ms）在图锁内执行，违反本文件 docstring 声明的「embedding/LanceDB 操作绝不持图锁」不变量——删除期间每轮系统提示的 snapshot/搜索全部冻结。挪到锁释放后（锁内只做内存删除 + _save）。
- **confirm 并发共用 client**：_get_extract_llm 已创建后的快路径不持锁——confirm 弹窗的 LLM 兜底可与后台抽取线程并发共用同一个专用 httpx.Client（模块明确声明非线程安全）。_describe_code_purpose 在使用期间持 `_fact_extract_lock`（非阻塞，拿不到说明抽取正在进行，退回启发式描述）。
- **JSON 结构校验**：graph_memory._load 与 memory._JsonStore._load 只捕解析异常——「合法 JSON 但结构错误」（顶层 list、entities 为 list）让存储永久不可用且无备份。加 isinstance 校验，坏文件告警后按空图继续。

#### 11.25.5 UI 层（#115，4 项）

- **窗口几何持久化全平台失效**：QSettings.value 回读 QByteArray（实测），`isinstance(geo, bytes)` 永假——用户每次启动都要重调窗口。_as_bytes 兼容 QByteArray/bytes/str。
- **同步 handler 兜底死代码**：SyncKnowledgeWorker 把临时 handler 引用挂在 worker 上，MainWindow 的兜底方法却读 window 自身属性（永远 None）——terminate 后 handler 闭包强引用整个 worker + RAGEngine（数百 MB）阻止回收。兜底改为显式传 worker（finished 槽 connect 时默认参数快照 + closeEvent terminate 路径显式调用）。
- **fetch 完成槽破坏忙碌态**：无条件解锁按钮/复位进度条——agent 运行中出现假空闲态；失败弹窗阻塞事件循环停摆流式渲染。按 `not (busy or _fetch_busy)` 合成规则设置，agent 运行中失败只进状态栏/日志。
- **reasoning 未攒批**：content 路径已用 100ms 定时攒批，reasoning 仍是每 chunk 五步光标操作——推理模型思考流量不低于正文，思考区越长越卡。复用同款 `_reason_buf + QTimer`（发送/清空对话/工具边界同步清缓冲与落地）。

### 11.27 语义切片静态嵌入快路径（#118）

#### 11.27.1 问题：切片阶段的隐性开销

修完 #116 的 docling 瓶颈后，下一层开销浮出：chonkie 语义切片的嵌入走共享 nomic 适配器（768 维 BERT ONNX 推理）。chonkie 的窗口方案对每个长章节做 **2N 次 embed**（N-3 个窗口段落 + N-3 个句子），而 `_DELIM` 含中文逗号——N 极大（88k 字符 ≈ 6000 句 ≈ 1.2 万次 embed）。实测吞吐 ~130 条/s，单章节 90-150s；长章节多的书切片阶段累计分钟级。

关键洞察：切片决策只比较**相邻窗口的相对相似度**（找主题断裂点），不需要与检索向量同空间——用 nomic（137MB BERT）做这件事是用高射炮打蚊子。

#### 11.27.2 修复：model2vec 静态嵌入快路径

嵌入后端解析链（`semantic_chunker.semantic_chunk_text`）：

```
显式注入 embedding_function（测试/外部） → _ChonkieEmbeddingAdapter
        ↓ 无注入
model2vec 静态嵌入（potion-base-32M，AutoEmbeddings 快路径）
        ↓ 构造失败（model2vec 缺失/模型下载失败）
共享 nomic 单例 → 适配器（慢但正确，与旧版行为一致）
        ↓ 也失败
返回 None → 上层回退递归切片
```

- **potion-base-32M**：model2vec 静态嵌入 = 词向量查表 + 平均池化，纯 numpy 无 BERT 前向；chonkie 官方默认后端，`AutoEmbeddings` 按 `minishlab/*` 前缀路由到 `Model2VecEmbeddings`。权重 ~30MB 首次使用时下载（HF 缓存）
- **实测**：88k 字符章节 90-150s → **0.4s（~250 倍）**；切片 450 个，token 分布 110-289（均值 229），在 [min_chunk_size, chunk_size] 契约内
- **依赖声明**：pyproject `[rag]` extras 与 rag/deps.py（`chonkie 可用且 model2vec 缺失` 才提示——chonkie 都没有时语义切片整体回退递归，model2vec 无意义）双双补充，缺失时同步前自动安装；`_get_static_embeddings` 失败走 60s 负缓存，安装完成后的下一次同步自动热升级到快路径
- **线程安全**：模块级单例 + 双重检查锁；model2vec `encode` 无状态，4 worker 共享同一实例

#### 11.27.3 验证

新增 4 项测试：deps 条件三态（chonkie 有/无 × model2vec 有/无）、后端选择（potion 可用时 SemanticChunker 收到静态嵌入实例）、nomic 回退、全缺失返回 None。test_semantic_chunker 10/10、test_deps 全过（应用环境）；基线回归 231 passed。既有 topic_ef 注入路径行为不变（适配器直通）。已知取舍：静态嵌入的语义精度弱于 BERT，切片边界质量略有差异（仍在 min/max 契约内）；切片决策与检索向量不再同空间（影响仅为边界位置选择，检索打分仍用 nomic）。

### 11.28 OCR 原生缓存滞留与周期回收（#119）

#### 11.28.1 问题：重启后内存仍达 17GB

#116 修复后用户重启应用重新同步，进程内存仍快速涨到 16.95GB（后续实测稳定 18-19GB）。top 取证给出决定性线索：19GB footprint 中 **17GB 是压缩内存（cmprs）**、purgeable 为 0——这是真实的脏内存：分配后未释放、久不触碰被系统压缩。时间线：本轮 OCR 了两本扫描书（神的历史 ~400 页、天主教灵修学史）+ docling 一个 epub。

#### 11.28.2 归因：三层实验排除法

1. **CoreML EP 合成图像实验**（120 次变尺寸调用，45 种形状组合）：RSS 在 1.2-1.5GB 波动后回落，**不累积**——排除「CoreML 按形状编译缓存」的直接嫌疑，也证明 fastembed 嵌入（CPU EP、动态长度、实测 tokenizer）与此无关。
2. **真实页面复现**（神的历史前 60 页走完整路径：`dpi=200` 灰度渲染 → `_ocr_preprocess` → 引擎）：**滞留 ~35MB/页**（60 页 +2114MB），与 400 页 ≈ 14GB 吻合。合成小图触发不了——只有真实 200dpi 大页 + 密集文字框（大 det 输入、大批量 rec crop）才会撑大 CoreML/ORT 按形状保留的原生工作集。
3. **对照验证**：同 60 页、每 20 页重建引擎 → 滞留 **+554MB**（9MB/页），内存锯齿状钳制在 1-3GB。

另注意：muPDF 的 store 缓存解码后满页位图（~10MB+/页），数百页累计可观——全书解析完收缩（`fitz.TOOLS.store_shrink(100)`）。

#### 11.28.3 修复：周期重建 + store 收缩（parsers.py）

- **`_OCR_RECYCLE_PAGES = 60`**：每书每 60 页 OCR 强制 `release_ocr_engine()` + 局部引用置 None，下一页懒加载重建——冲刷全部 CoreML/ORT 原生缓存。峰值滞留钳制在 60 × 35MB ≈ 2GB；代价每 60 页一次 ~6s 引擎重载（相对每页 5-12s 的 OCR 可忽略）。release 只清进程级单例引用，其它 worker 持有的局部引用由引用计数保活，并发安全。
- 全书 `doc.close()` 后：`fitz.TOOLS.store_shrink(100)`（收缩进程级 MuPDF store，其它 worker 只是缓存失效需重解码，正确性不受影响）+ `gc.collect()`。

> **#123 补遗**：上式的「局部引用置 None」只对触发回收的 worker 生效——引擎此前被缓存在每个 worker 的**循环级局部变量**里，其余 worker 仍抱旧引擎继续用，最多 4 代引擎的原生缓存并存（实测内存仍 16G→12G 锯齿）。修复：引擎改为**每页从进程级单例取用、页末释放**（不做 worker 级缓存），回收置 None 后所有 worker 下一页统一重建，任意时刻至多一代引擎存活。

> **#130 补遗（回收周期 60 → 20 → 50）**：#124 凭水位倒推把周期收到 20（热重建当时按冷启动 ~6s 估）。#130 用真实 200dpi 页系统扫描 N=10..100 后修订：热重建仅 **1-2s/次**（冷启动 3-4s 全程只一次），各 N 的峰值足迹持平 ~5.2GB（压缩器吸收缓存增长，peak_cmprs 随 N 线性涨），N 对 400 页书总耗时影响仅 1-3%。定 **N=50**：单代水位 ~1.8GB、重建摊销 ~0.5%，实测的速度-内存平衡点。

#### 11.28.4 方法论警示

**合成图像实验复现不了此问题**：45 种形状、120 次调用仅 1.2GB 工作集且会回落。必须用真实文档的真实渲染路径做实验（本轮先用合成图差点得出「CoreML 无罪」的错误结论）。top 的 `cmprs` 列（压缩内存）是识别「分配后遗忘」型滞留的关键指标——活跃工作集看 mem-cmprs 差值。

基线环境 test_parsers + test_docling_parser 15/15 通过（应用环境 3 个失败经 stash 对照确认为预先存在的环境错配：测试伪造 rapidocr 1.x 模块，应用环境装有真实 3.x 导致 fake 不被使用，与本改动无关）。

### 11.29 ingest 文件分片 LPT 负载均衡（#120）

#### 11.29.1 问题：空片与负载倾斜

用户观察日志「Worker-928 启动，负责 0 个文件」——分片按 `ceil(n/workers)` 连续切片，n=9、workers=4 时 `chunks_per_worker=3`，第 4 片 `[9:12]` 为空。连带问题：文件按 rglob 名字顺序连续分配，扫描书（逐页 OCR，30+ 分钟）扎在同一片时，其他 worker 早早完成长时空转，同步总时长被最慢片决定。

#### 11.29.2 修复：`_shard_files_balanced`（LPT 调度）

文件按**大小降序**，每次分给「累计字节数最小 → 并列时已分配文件数最少 → worker 序号」最小的 worker：

- 最大的 `num_workers` 个文件必然分属不同 worker（慢书摊开）
- n ≥ workers 时空片不可能出现；并列时的文件数二级键保证 n < workers 时也尽量均匀
- `os.path.getsize` 失败（TOCTOU）按 0 处理，worker 内已有逐文件异常隔离
- 大小只是时长的近似（扫描书按页 OCR、文本书直读），但显著优于随机序连续切片

#### 11.29.3 验证

新增 tests/test_sharding.py 6 项：9/4 无空片、最大文件分属不同 worker、等大均分 [3,2,2,2]、极端大小分布贪心优于连续切片、TOCTOU 容错、单 worker 直通。6/6 通过。

### 11.30 重排模型缓存错配与嵌入吞吐瓶颈（#121-#122）

#### 11.30.1 重排模型每次同步重复下载（#121）

用户观察「每次都下载重排模型」。三重错配：

1. `_download_reranker_model` 调 `TextCrossEncoder(...)` **未传 cache_dir** → fastembed 的 `define_cache_dir(None)` 落到**系统临时目录** `/var/folders/.../T/fastembed_cache`（实测权重确实在这里，1.2GB）——macOS 定期清理临时目录 → 清完即重下 570MB。与嵌入模型当初修过的「临时目录被清理导致重复下载」完全同构，重排路径漏了同样的修复。
2. `_is_reranker_cached` 检查 `define_cache_dir("local_cache")`——**相对路径参数按 CWD 解析**（`<项目根>/local_cache`，无意义位置）→ 永远判定未缓存。
3. 结果：每次同步都走一遍下载流程（文件在临时目录时是秒级校验；被清理后是真下载）。

**修复**：下载显式传持久目录 `~/.cache/fastembed`（`_get_fastembed_cache_dir()`，与嵌入模型同处）；检测经 `_reranker_cache_roots()` 兼容持久 + 临时两个根，仍只认真实权重文件（防中断下载误判）。切到持久目录后的第一次同步会补下载一次，此后不再发生。

#### 11.30.2 嵌入吞吐瓶颈与「假卡死」（#122）

用户报告同步长时间无输出、内存/CPU 高企。逐层测量定位：

| 实验 | 结果 |
|---|---|
| 真实切片（32 × ~900 tokens）CPU EP | **309-338s/子批，39 tok/s**，RSS +4.1GB |
| 默认线程 / threads=8 / threads=4 | 57 / 63 / 51 tok/s——线程非瓶颈 |
| CoreML EP | 仅 588/1422 节点可用（nomic 的 rotary 结构大量算子不支持），三次 SIGKILL（混杂 32 批 / lazy 加载 / **长度分桶 12 批均复现**）——不可用 |
| torch-MPS | nomic 官方自定义建模代码与 MPS 运行时不兼容（`get_extended_attention_mask` 缺失）——死路 |
| fp32 完整版 vs int8 量化版 | 36 vs 39-63 tok/s——**量化不是原因**（慢在 BERT-large × 长序列注意力） |
| 语义切片 potion 快路径 | 0.4s/88k 字符——切片不是瓶颈 |

**真正根因：fastembed 批内所有序列 padding 到批内最长**。切片长度天然混杂（800-2000 字符），一个 1900 字符的长切片强迫同批 31 个短切片全部按它的长度计算——padding 浪费 2-4 倍；再叠加 O(L²) 注意力对批内最大长度的敏感性，混杂大批吞吐被压到 40 tok/s（短文本实测 1280 tok/s，佐证）。

**修复：按文本长度降序分桶 + 12 条/子批**（`_embed_chunks`；子批大小后由 #125 改为实测自适应，见 11.31）：

- 排序后批内长度相近，padding 浪费归零；向量按原序回填，结果与混杂批完全一致
- 实测（195 个真实切片端到端）：**69.8s ≈ 1676 tok/s，~18 倍**；全库 4000 切片从 8-19h → **约 25-30 分钟**
- 内存：批内长度相近后激活峰值 ~2.7GB（原 4.3GB）；降序使最长批最先出现，提早顶到水位后逐批变轻
- 附加：子批级进度日志（消除 5 分钟静默的「假卡死」）、ORT `threads=4`（留半核给 OCR worker）
- 无需换模型、无需表迁移——nomic 的 768 维与 8192 上下文完全保留

如实记录的失败路（避免后人重走）：CoreML EP（41% 节点 + SIGKILL×2）、torch-MPS（自定义代码不兼容）、线程调优（±10%）、fp32 替换 int8（速度相同）。

**后续项**：`rag_embedding_model` 配置已存在（全链贯通），切 `bge-small-zh-v1.5` 需 512 维表迁移 + chunk_size 联动（512 截断）；分桶优化后收益已不紧迫，按需排期。

### 11.31 嵌入子批大小自适应（#125，#126 生产验证修订）

#122/#124 将子批定为固定 12 条（内存 ~2.7GB 与吞吐的平衡点），但该平衡点随环境漂移：OCR worker 抢占 CPU 时大子批吞吐下跌、独占 CPU 时小子批又浪费 GEMM 效率。#125 将固定常量改为 `_SubBatchTuner` 实测自调；#126 经合成基准（2-50 全尺寸扫描、双档长度分布、6GB 护栏）与真实切片生产路径（真实知识库 200 切片 × 生产代码，tuner vs fixed2/4/12 四模式对照）双重验证后**修订方向与范围**：

- **硬件事实（#126 修订依据）**：真实切片上吞吐与内存都随子批增大**单调变差**——size2 = 2071 tok/s @ 1.28GB、size4 = 1864 @ 2.14GB、size12 = 1163 @ 4.99GB。激活工作集 ∝ 子批×批内最长序列，超出 CPU 缓存后被内存带宽卡死，「大批次摊薄 GEMM 开销」在这台机器的 CPU EP 上不成立。合成基准还实测了热节流假象：被同步任务污染时小尺寸吞吐减半、出现「中等尺寸最优」的假峰（干净重测后消失）。
- **范围与步长**：[1, 5]，初始 2，步长 1（#126 修订方向，#127/#128 用户定参：初始 2 起步即落在实测最优区，步长 1 在平坦段精细寻优）；窗口 = 2 个子批聚合一次判定。
- **度量**：不用原始 tok/s（长度分桶后批与批的序列长度天然不同，直接比有系统性偏差），改用算力速率 `ops/s = n × max_len² / dt`（字符数为 token 的单调代理），对批大小与批内最长长度同时归一，跨窗口、跨尺寸可比。
- **爬升**：基线窗口 → 试探 +1 → 速率 ≥3% 提升才采纳（低于视为噪声，避免平坦段抖动）并继续上调；变慢则**回退到上一个数字**进入监控。5 封顶。
- **降档**：监控阶段 EMA（α=0.5）连续 2 窗口低于历史最优 75% → 降 1 避让，下限 1；历史最优逐窗口 ×0.999 衰减，环境永久变慢后不拿旧峰值当标尺。
- **重新爬升**：监控阶段速率比历史最优高 10%（如 OCR worker 结束、CPU 空出）→ 从当前尺寸重新爬山，避免永远停在忙时降下来的小尺寸上。
- **恢复分支（#129，消除降档单向棘轮）**：降档触发只需连续 2 窗口 <75% 最优（一次内存尖峰的短暂变慢即可），回去却需 >110% 最优（平台期不可能达到）——用户实测「用 2 跑了一段时间、内存冲高一下就降到 1 再也不回去」。monitor 新增恢复：速率回到历史最优 **95%** 且当前尺寸低于最优尺寸（`_best_size`，随爬升采纳/回退/封顶出口重锚）→ **直接步回最优尺寸**。不走完整爬山的原因：plateau 上试探必然持平（<3%）被回退，回退锚把最优尺寸永久改小，恰好复现卡死；直接步回后留在 monitor，若最优尺寸在新环境下确实过慢，降档路径再次接管，自校正无循环。恢复判定放在 best 更新之前，防止恢复窗口把 best/best_size 就地改写成小尺寸。
- **RSS 软墙 8GB（#129，用户定参，无闩锁）**：内存偶尔冲高是正常波动（OCR 缓存、压缩计费），超墙时每个子批 `force_down()` 降 1 档（激活随之变小、RSS 自然回落），回墙下即停，恢复交给恢复分支。与已弃用的 5GB 闩锁版的本质区别：无 `mem_pressed` 标志、降档不永久、阈值高于真实同步基线（6-10GB）的常见水位。psutil 缺失时静默跳过。
- **内存安全：形状预算（#126 修订，替代 RSS 守卫；#138/#139 改为后端感知 + 保底下限）**：嵌入激活 ∝ 条数 × 批内最长序列²——`_embed_chunks` 组装每个子批时按 `_shape_cap_size` 钳制：`min(size, max(_SUBBATCH_MIN, budget // max_len²))`。预算**按后端取**（`model_backends._EMBEDDING_SHAPE_BUDGET`）：mlx 走 flash attention、内存 O(S)，`300M` → B=4@8192（实测 ~1GB）；onnx(CPU) 物化注意力、内存 O(S²)，`150M` → B=2@8192；无/未知后端沿用 `6M`（size8 × 1311² ≈ 13.75M 单位 ≈ 4.7GB 激活 → 6M ≈ 2GB）。**下限 2 条、禁止夹到 1**（#139 用户定参）：单条长切片吞吐塌到最优的 50-69%，且模型加载 / ONNX 会话初始化的固定成本被单条摊得极薄；请求本身不足 2 条时按请求返回，不为凑下限放大批次。**不用绝对 RSS 阈值**：真实同步进程基线本就有 6-10GB（OCR 原生缓存、LanceDB 等），5GB 绝对阈值在首个子批即触发 force_down 并因 RSS 永不回落而永久卡死在下限——生产实测「子批很快降到 1」的根因。调优器 report() 收到钳制后的实际条数，状态机在可行域内正常爬山。嵌入函数内部（`_embedding_batch_for`）用同一组预算，直接调用路径（SkillRetriever、graph_memory）与 RAG 入库路径行为一致。
- **预热丢弃（#126 修订）**：首个完整窗口包含模型加载 / ONNX 会话初始化（可达 10s+），会把爬升基线拉到虚低，让热身的试探窗口显得「暴涨」被误采纳——首个窗口只用于预热，丢弃不计入判定。
- 状态由锁保护（`add()` / `add_streaming()` 可能来自不同线程）；进度日志带 `[size=N]` 与实时速率，调参过程可观测。

验证：`tests/test_rag_subbatch_tuner.py` 17 项（#129 新增恢复 2 项、软墙 1 项、重爬改 1 项），RAG 相关 133 项通过。生产验证数据：tuner 旧版端到端 1313 tok/s @ 3.72GB → 修订后预期 ~2071 tok/s @ 1.28GB（+58% / 内存 −65%）。

## 附录 A：关键性能优化

1. **流式 token 速度估算**：增量计数 `live_est_tokens += _estimate_tokens(chunk)`，每 0.3s 发射一次；总开销 O(N) 而非 O(N²)（避免每 0.3s 全量 join + 扫描）。
2. **TTFB 排除**：速度计算用 `gen_elapsed = now - ttfb`（不含 prefill 延迟），准确反映生成速度。
3. **chunker 增量计数**：维护 `cur_cjk` / `cur_other` 运行计数，避免 O(N²) 重复扫描。
4. **RAG 流式 ingest**：worker 池并行 + 有界队列背压 + 批量 embed，内存占用 O(workers × 单文件 chunks) + O(batch_size)，不随知识库总规模线性增长。
5. **OCR 全局单例**：4 worker 共享同一 RapidOCR 实例（~500MB），信号量仅串行化其 `engine(img)` 调用（ocrmac 路径可并发），避免 ~2GB 重复加载。
6. **LanceDB 表不缓存"不存在"**：`_ensure_table()` 每次重查 `table_names()`，因为 SyncKnowledgeWorker 可能已创建表；目录 listing 很便宜。
7. **`list_sources` 用 pyarrow compute**：在 Arrow 层去重，避免把全部行转 Python 对象。
8. **子批次嵌入释放 GIL + 长度分桶**：`_embed_chunks` 将每批 200 个 chunk 按文本长度降序排序后拆为 12 条/子批——批内长度相近使 padding 浪费归零（混杂批 padding 浪费 2-4 倍算力，实测分桶后嵌入吞吐 ~18 倍，#122），且**累计**持 GIL 达到阈值才让出（不是每个子批都 sleep），让主线程 QTimer 能插入执行消费日志缓冲区，避免 ONNX Runtime 长时间持 GIL 导致 UI 冻结。ORT intra-op 线程固定 4（留半核给 OCR worker）。
9. **QTimer 日志轮询**：同步期间用 100ms 间隔的 QTimer 直接在主线程事件循环中轮询 `_log_buffer`，绕过 Qt queued signal 机制（后者在 GIL 被占用时无法及时处理）。
10. **图谱观察批量嵌入**：`_index_observations_batch()` 用 `embed_documents()` 单次 ONNX 前向处理整批观察（事实抽取一次对话通常产生多条观察），替代逐条 `embed_query()` 的 N 次调用。
11. **技能索引防抖**：`SkillIndex` 以目录 mtime + 300s 间隔双重条件触发重建，常态 `skill_search` 只读 `_index.json`（O(1) 加载），不重复扫描目录。
12. **docling 单例**：`DocumentConverter` 进程级单例 + 双重检查锁，多 worker 共享一份 docling 模型（torch 模型重，避免重复加载）。
13. **Hybrid 分片三级回退**：结构+语义 → 纯语义 → 递归，chonkie/embedding 缺失时自动降级，不阻塞入库；语义分块复用向量存储的 nomic-embed-text 单例，避免加载第二份 ~137MB ONNX 模型。
14. **动态并发**：`num_workers = min(parallel_workers, len(files))`，文件数少于默认并发时按文件数缩减；哨兵计数 `expected_sentinels = num_workers`（与实际启动线程数一致），避免文件数不足时消费者空等 15s 兜底超时。
15. **混合检索召回增强**：向量相似度 + BM25 关键词双通道并行检索，兼顾语义召回与精确关键词命中；BM25 用 jieba 预分词（Python 层）+ 原生 FTS `simple` tokenizer。
16. **jieba 分词器单例**：`_get_jieba()` 进程级缓存 + 双重检查锁，避免每个切片重复初始化 jieba 词典（首次加载 ~0.7s）。
17. **文档元数据缓存**：`VectorStore._documents_cache` 缓存 documents 表内容，`get_document_digest`/`list_documents` 避免每次全表 `to_pylist()`；写入时失效。documents 表**不再存全文 Markdown**（只存 digest + chapters + md_path），缓存按列读取并剔除 markdown 列——既省磁盘第三份冗余，也避免整库常驻内存。
18. **Reranker 加载状态机**：`_get_reranker` 用 `_reranker_state`（idle/loading/done/failed）去重并发加载，避免多调用方各自起加载线程（每线程 ~500MB PyTorch 权重泄漏）；超时后后台线程完成仍写入结果供后续复用。
19. **OCR 引擎释放**：`parsers.release_ocr_engine()` 在 `RAGEngine.close()` 时释放全局 RapidOCR 单例（~500MB），避免 GUI 应用同步含图片 PDF 后常驻内存；下次入库懒加载重建。
20. **独立事实抽取客户端**：`Agent._get_extract_llm()` 为事实抽取 daemon 线程惰性创建独立 `LLMClient`（独立 `httpx.Client` 连接池），避免与对话线程并发争用同一个非线程安全的 `httpx.Client`；`Agent.close()` 释放该独立客户端，防止「应用配置」重建时泄漏连接池。
21. **`_estimate_tokens` 用 `str.translate`**：CJK 字符数通过预编译的删除表在 C 层统计，替换原先的 Python 逐字符循环（该函数在 token 速度估算、上下文收缩阈值判断等热路径上高频调用）。
22. **`estimate_tokens` 用 `finditer` 计数**：原来 `re.findall` 会把全部匹配物化成列表（整篇中文文档 = 数万个临时单字符串对象）；改为预编译 `_CJK_RE` + `sum(1 for _ in finditer(...))`，零中间列表。
23. **切片去重只存哈希**：`_split_by_tokens` 的 `seen` 集合原来存每个 chunk 全文（切片本身已是文档副本，等于峰值内存翻倍）；改为存 `hash(chunk)`。
24. **段落分组增量计数**：`hybrid_chunker._split_by_paragraph` 原来每追加一段就重新估算整个 `current`（O(n²)）；改为维护 `current_tokens` 运行计数。
25. **技能扫描只 stat 目录与 `SKILL.md`**：`SkillScanner._dir_mtime()` 原来 stat 每个文件，且 `_should_scan()` 与 `scan()` 各调一次 —— 单次检索两遍完整 `os.walk`。
26. **技能索引按 workspace 缓存**：`SkillIndex` / `SkillRetriever` 按目录路径缓存，避免切换 workspace 后重建，也避免错误复用。
27. **BM25-only 候选复用查询向量**：`SkillRetriever` 只为「仅 BM25 命中」的候选算一次 query 向量并复用，替代每个候选各跑一次 `embed_query`。
28. **`skill_retriever.sync()` 只取两列**：`to_arrow().select(["dir","fingerprint"])`，不再把两条 768 维向量列转成 Python float 列表。
29. **`list_sources` / `list_documents` 走缓存与列裁剪**：避免把 documents 表反复全量 `to_pylist()`。
30. **日志/对话控件限流**：`think_view` 10000 段、`log_view` 5000 段、`chat_view` 5000 段（`setMaximumBlockCount`），长会话不再无限增长。
31. **写入侧 source→hash 缓存**：`_embed_chunks` 内按批次缓存 `_hash_source`（同批 chunk 通常同源），避免每 chunk 重算 md5。
32. **tools schema 缓存**：`ToolRegistry.schemas()` 自身缓存 schema 列表（工具表变动时失效），`_tool_schema_tokens()` 复用之并按 `_schema_version` 版本号缓存 token 数——命中时零序列化，避免每轮迭代为上下文收缩阈值重复 `json.dumps` 全部工具 schema（MCP 工具多时是几十 KB JSON × 每轮多次）。
33. **当天事实与技能注入限流**：系统提示的动态注入段不在上下文收缩范围内，故设条数/字符上限，长会话下避免提示单调膨胀（详见 11.19.6）。

## 附录 B：已知约束

1. ~~**`code_run` 超时无法强杀线程**~~ **（已解决，见 11.20.1）**：改为受限子进程执行，超时走 SIGTERM → SIGKILL `killpg`，整棵进程树被真正杀掉。仅当找不到可用 Python 解释器时才回退到进程内 `exec`（此时仍有原限制）。
2. **MCP 工具默认 destructive**：所有 MCP 工具需用户确认，无法细粒度区分安全/危险操作。
3. **单进程单 agent**：不支持多 agent 并发对话；`_history` 是实例属性，非共享。
4. **RAG 不支持增量删除单 chunk**：`delete_by_source` 删整个 source 的所有 chunk，无法精确删除单个 chunk。
5. **摘要 LLM 调用无独立超时**：`_summarize_via_llm` 复用 `chat_stream`，依赖 LLMClient 的结构化 read 超时（每 chunk 最大间隔 60s），无更细粒度的独立控制。
6. **事实抽取 best-effort + 异步**：`_maybe_extract_facts_async` 在 daemon 线程中调用**独立的 LLMClient**（`_get_extract_llm()`，独立 `httpx.Client` 连接池），LLM 失败时静默跳过，不重试。用户关闭应用时 daemon 线程可能被强制终止（未完成的抽取会丢失）。
7. **图谱向量索引非事务**：JSON 图谱文件和 LanceDB 向量索引不是事务性写入，极端情况下（进程崩溃在两者之间）可能出现不一致。
8. **Embedding 单例不释放**：共享的 FastEmbed ONNX session 在进程退出前不 `release()`，仅由 OS 回收。这是设计选择——RAG 和图谱可能交替使用，提前释放会导致另一方崩溃。
9. **技能索引非实时**：`SkillIndex` 防抖扫描以「目录 mtime 变化」为触发条件；直接编辑已有技能目录内的 `skill.json` 内容不会改变目录 mtime，元数据变更最迟在 300s 间隔后才会被索引收录（新增/删除技能目录会立即触发）。
10. **Prompt 体积**：SYSTEM_PROMPT 精简至 ~200 tok + 动态注入（work memory 手动 scratchpad / 当天自动抽取事实 / KB 状态 / 命中技能）。长期记忆**不注入** prompt，靠 `memory_search` 工具按需检索。目录化技能的完整指令不进系统提示词，由 `skill_load` 按需读入。动态注入段**不在上下文收缩范围内**，因此各有上限（事实 ≤20 条/2000 字符，技能 prompt ≤1500 字符）；抽取侧限 ≤5 实体 × 3 观察，持久化桶 ≤200 条。
11. **docling 环境约束**：docling 依赖 `pyarrow<17`，而 pyarrow 16.x 无 Python 3.13 的预编译 wheel，导致 Python 3.13 环境无法安装 docling（需 Python 3.10–3.12）。docling 未安装时系统自动回退到按格式的轻量解析器，功能不受影响，仅失去统一解析/布局理解能力。
12. **BM25 索引重建开销**：LanceDB 的 FTS 索引不会在 `add()` 后自动增量更新，需 `replace=True` 重建。写入侧现在**只置脏、推迟到下次检索惰性重建**（旧实现每次 `add()` 都全库重建，一次同步 N 批 = N 次），全量重建大知识库时仍有这一次开销。
13. **code_run 泄漏线程追踪上限**：仅在**进程内兜底路径**（找不到可用解释器）才会产生泄漏线程——`_leaked_threads` 追踪列表限制最多 10 个。子进程路径下超时可被强杀，无泄漏线程；`_cancelled()` 协作取消在两条路径都可用（子进程侧通过取消标志文件实现）。
14. **`skill_load` 默认入口是 `SKILL.md`**：老体系目录技能在 `skill.json` 里声明 `entry: prompt.md`，工具会在 `SKILL.md` 缺失时回退到声明的入口，再回退到 `prompt.md`。
15. **技能请求计数表有上限**：`skills.json` 的 `requests` 超过 500 条时淘汰最旧的一半，避免长期使用时文件与内存无界膨胀。
16. **共享 Embedding 单例加载失败会被重试**：`_shared_embedding_function()` 只在成功时置位，失败不缓存，网络恢复后语义切片会自动恢复（而不是本进程内永久降级到递归切片）。
17. **UI 测试需要 `pytest-qt`**：`tests/test_bridge.py`、`tests/test_integration.py`、`tests/test_ui_flow.py` 依赖 `qapp` fixture；未安装时这三个文件的用例会在 setup 阶段报 `fixture 'qapp' not found`（已加入 `pyproject.toml` 的 `test` 分组）。
