> 本文档基于 `src/agent/` 当前实现编写，覆盖系统概览、架构、模块职责、核心数据流、线程/并发模型、资源管理、错误处理、配置体系与扩展点。

## 1. 系统概览

### 1.1 定位

Base Augment Agent 是一个**本地自主 Agent**：

- **本地优先**：所有工具执行、文件操作、知识库向量检索都在本地完成；唯一的外部网络依赖是 LLM API（OpenAI 兼容）。
- **图形界面**：基于 PyQt6 的桌面应用，提供对话、思考过程、日志三栏式交互体验。
- **可插拔工具**：内置 13 个工具 + MCP 协议接入远程工具，工具以「类 + schema」形式注册，由模型自主调用。
- **本地 RAG 知识库**：自动解析文档、清洗、切片、向量化、LanceDB 存储、BGE 重排序，全程离线。
- **上下文自管理**：主动摘要 + 被动收缩，避免超出 LLM 上下文窗口；摘要持久化到 `workspace/memory.md`。

### 1.2 技术栈

| 层 | 技术 |
|----|------|
| UI | PyQt6（QMainWindow / QThread / pyqtSignal） |
| LLM 传输 | httpx（流式 SSE） |
| 工具系统 | 自研 `Tool` 抽象 + MCP JSON-RPC over stdio |
| 向量存储 | LanceDB（本地 Lance 列式格式） |
| 嵌入模型 | FastEmbed (ONNX Runtime) — `nomic-ai/nomic-embed-text-v1.5` |
| 重排序 | FlagEmbedding — `BAAI/bge-reranker-base` |
| 文档解析 | python-docx / openpyxl / python-pptx / PyMuPDF / ebooklib / bs4 / RapidOCR |
| 持久化 | JSON 文件（config / memory / skills / manifest） |

### 1.3 入口

[main.py](file:///Users/arlenecc/codebase/base-agent/main.py) 将 `src/` 注入 `sys.path`，调用 [agent.ui.main_window.run()](file:///Users/arlenecc/codebase/base-agent/src/agent/ui/main_window.py)，后者构建 `QApplication` + `MainWindow` 进入 Qt 事件循环。

### 2.2 关键设计原则

1. **UI 线程绝不阻塞**：所有耗时操作（LLM 流式调用、RAG ingest、依赖安装、模型列表获取）都在 QThread 中执行；UI 通过 `pyqtSignal` 接收事件。
2. **回调驱动的协议**：Agent 通过 `AgentCallbacks` 抽象与外界通信，UI 层用 `Bridge` 把回调转成 Qt 信号，实现线程安全。
3. **资源显式释放**：ONNX Runtime / LanceDB / MCP 子进程 / httpx 连接都通过 `close()` / `shutdown()` 显式释放，不依赖 Python GC。
4. **协作式取消**：所有长任务都有取消标志（`threading.Event`），在文件/批处理边界检查后退出，不强制 kill。
5. **原子写**：所有 JSON 持久化（config / memory / skills / manifest / memory.md / 文件写入）都使用 temp + `os.replace()` 原子写。
6. **工作区沙箱**：文件工具用 `realpath` 解析并前缀检查，符号链接逃逸也被拒绝；`code_run` 通过 `builtins.open` 守卫拦截工作区外的写操作。

- `max_iterations`（默认 15）：每个 turn 最多推理迭代数。

#### 3.6.5 [vector_store.py](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py) — 向量存储

**`FastEmbedEmbeddingFunction`**：
- `nomic-ai/nomic-embed-text-v1.5` via ONNX Runtime，~130MB 量化后，离线可用。
- **文档/查询前缀**：`search_document: ` / `search_query: `（nomic 模型要求）。
- 懒加载，首次调用才下载模型。

**`VectorStore`**（[L76-660](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py#L76-L660)）：
- **`_ensure_table()`**：每次调用都重查 `table_names()`（不缓存"表不存在"），因为 SyncKnowledgeWorker 可能已创建表。
- **`add_streaming`**（[L254-411](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py#L254-L411)）：流式写入，内存占用 O(batch_size) 而非 O(总 chunks)。
  - 第一批特殊处理：决定是 `create_table` 还是 `add` 到已有表。
  - 已有表：按 source 的 md5 hash 用 `id LIKE '{hash}_%'` 删除旧记录（upsert 语义）。
  - 批量 20 条/批。
- **`_embed_chunks`**：将每批 20 个 chunk 再拆分为 5 条/子批进行 embedding，每个子批次完成后 `time.sleep(0.01)` 释放 GIL，让主线程的 QTimer 有机会轮询日志缓冲区并更新 UI。ONNX Runtime 的 `embed()` 在 C++ 计算期间持有 GIL，整批一次性嵌入会导致 UI 长时间冻结。
- **`search`**：向量归一化为单位长度后用 L2 距离模拟余弦相似度；`_distance` 转换为 `[0,1]` 相似度分数。
- **`search_with_rerank`**：初检 `top_k * 4` → BGE reranker 精排 → 返回 top_k。
- **`rerank`**：BGE 不可用时回退到距离排序；分数归一化到 `[0,1]`。
- **`close()`**（[L571-623](file:///Users/arlenecc/codebase/base-agent/src/agent/rag/vector_store.py#L571-L623)）：
  - 显式调用 ONNX `InferenceSession.release()` 立即回收 C++ 堆。
  - BGE reranker 的 PyTorch 模型 `model.cpu()` 后置 None。
- **`reload()`**：丢弃表句柄，下次操作重新打开。

#### 3.7.1 日志显示架构

知识同步期间的日志显示采用 **QTimer 轮询 + 线程安全日志缓冲区** 方案，而非传统的 Qt queued signal：

**两条日志通道**：
1. **QSignalLogHandler**（常态）：挂在 root logger 上，通过 `message_received` pyqtSignal 将日志安全传递到 UI 线程的 `log_view`。用于 Agent 对话、工具执行等常态日志。
2. **`_log_buffer` + QTimer 轮询**（同步期间）：同步期间 `QSignalLogHandler._sync_active=True`，跳过 RAG 日志避免与轮询并发操作 `log_view` 导致崩溃。RAG engine 通过 `log_callback` 参数直接把日志写入 `_log_buffer`（`threading.Lock` 保护），主线程的 `QTimer` 每 100ms 轮询消费 buffer 并 `appendPlainText`。

**为什么不用 Qt queued signal**：ONNX Runtime 在 `embed()` 期间持有 GIL 做 C++ 计算，Qt 的 queued signal 需要主线程事件循环处理，但 GIL 被占用时事件循环无法执行。QTimer 的 `timeout` 回调也是在主线程事件循环中执行的，但只要 `_embed_chunks` 的子批次 `sleep(0.01)` 短暂释放 GIL，QTimer 回调就能插入执行并消费 buffer。

**分工**：
- **日志区域**（`log_view`）：显示详细的全链路日志（扫描→对比→解析→清洗→切片→向量化→清理→保存）。
- **底部状态栏**（`status_label`）：只显示进度摘要（如"同步中 3/4 (75%) — 已写入 80 切片"），不显示完整日志行，避免重复。

## 4. 核心数据流

### 4.1 Agent 推理循环

```
用户输入
  │
  ▼
Agent.run(user_input)
  │
  ├─ skills.record_request(text)  ──→ 可能触发 on_skill_suggested
  ├─ history.append({user, content})
  ├─ _trim_history()  (max_history 上限，且不留下悬挂 tool 消息)
  │
  └─ while iteration < max_iterations:
       │
       ├─ [主动收缩] 若 _should_shrink_context() (estimate > 90% max_context_tokens):
       │     _shrink_context("主动收缩")
       │     continue   ← 不消耗 iteration
       │
       ├─ messages = [system_prompt] + history
       │   (system_prompt 动态注入 work_memory / long_memory / matched skill)
       │
       ├─ for ev in llm.chat_stream(messages, tools, temperature):
       │     ├─ "content"   → on_content(ev.content) + 累积 live_est_tokens
       │     ├─ "reasoning" → on_reasoning(ev.content)
       │     └─ "done"     → tool_calls, usage
       │   每 0.3s 发射一次 on_token_speed（用 generation 时间，排除 TTFB）
       │
       ├─ [被动收缩] 若 LLM 抛 context_length_exceeded:
       │     _shrink_context("被动收缩")
       │     iteration -= 1; continue   ← 不消耗 iteration，重试同一次
       │
       ├─ 累积 token 统计（API reasoning_tokens 优先，否则用估算值）
       │
       ├─ assistant_msg = {role: assistant, content, tool_calls}
       │   (补全缺失的 tool_call.id，用 call_{counter}_{idx})
       │   history.append(assistant_msg)
       │
       ├─ if no tool_calls: on_finished(); return content
       │
       └─ for tc in tool_calls:
            ├─ parse_args(raw_args)  ← 失败时报错给模型
            ├─ tool = registry.get(name)
            ├─ if tool.should_confirm(args) and not callbacks.confirm(msg):
            │     result = ToolResult(False, "User denied")
            ├─ else:
            │     on_tool_start(name, args)
            │     result = registry.execute(name, args)
            │     on_tool_end(name, result)
            └─ history.append(_tool_message(tc, result))   ← role=tool, tool_call_id 匹配

  (达到 max_iterations 或无 tool_calls 时退出)
```

**关键设计点**：
- **收缩不消耗 iteration**：用 `iteration -= 1` 让被动收缩重试同一轮；主动收缩用 `continue` 跳过本次循环（`iteration` 还未自增）。
- **`_shrink_keep_recent = 6`**：保留最近 6 条消息 verbatim；若切分边界落在 `assistant(tool_calls)` 之后，会把对应的 `tool` 结果拉回保留段，避免悬挂 `tool` 消息。
- **摘要持久化**：写入 `workspace/memory.md`（带时间戳 + 触发原因），原子写。
- **LLM 摘要失败回退**：`_fallback_summary` 用结构化摘要（用户请求 + 工具名列表），不丢工具调用轨迹。
- **Token 估算策略**：API 报告 `reasoning_tokens` 时信任 API；否则用 `_estimate_tokens(reasoning_text)` 估算并加到 total 上。

### 4.2 RAG 摄取流水线

```
ingest(force, progress_callback)
  │
  ├─ Step 1: 扫描 kb 目录 (rglob) → all_files
  │
  ├─ Step 2: 加载 manifest，分片
  │   ├─ 未修改（mtime + size 一致）→ 跳过，progress 回调
  │   └─ 新增/修改 → files_to_process
  │
  ├─ Step 3: 启动 worker 池（默认 4 线程）
  │   每个 worker 处理一个 file shard:
  │     ├─ extract_text(filepath)  ← 失败记录到 errors, 跳过
  │     ├─ 若 markdown 缓存有效（mtime ≤ 源文件）→ 读缓存
  │     │   否则 clean_text + normalize_markdown → 写 .md 缓存
  │     ├─ chunk_documents → doc_chunks
  │     ├─ 背压: q.put(item, timeout=2.0)  ← 队列满时阻塞
  │     └─ finally: q.put(_SENTINEL)
  │
  ├─ Step 4: 主线程消费队列
  │   _chunk_iter() 生成器:
  │     while sentinels_seen < parallel_workers:
  │       item = q.get(timeout=2.0)
  │       if item is _SENTINEL: sentinels_seen++; continue
  │       更新 manifest[filepath] = signature + content_hash + chunk_count
  │       for c in doc_chunks: yield c
│   store.add_streaming(_chunk_iter(), batch_size=20, on_batch)
│     ├─ 第一批: 决定 create_table 还是 add
│     ├─ 按 source hash 删除旧记录 (upsert)
│     └─ 每 20 条 embed + add 一次（内部再拆分 5 条/子批，子批间 sleep 释放 GIL）
  │
  ├─ Step 5: _cleanup_deleted_files
  │   manifest 中存在但 all_files 不存在的 → store.delete_by_source + 移除 manifest 条目
  │
  └─ Step 6: _save_manifest (原子写)
```

**关键设计点**：
- **背压机制**：`queue.Queue(maxsize=parallel_workers * 2)`，worker 超前产出时阻塞，避免内存堆积。
- **取消传播**：`_cancelled` 在 worker put 循环、主线程 get 循环、extract 前等多处检查；`store.add_streaming` 失败时主动 `cancel()` 让 worker 停止产出。
- **Sentinel 丢失保护**：若所有 worker 已退出但 sentinels 未收齐，主线程退出避免死锁。
- **Markdown 缓存**：基于源文件 mtime 判断是否需要重新解析，避免重复 OCR/PDF 解析。
- **日志实时显示**：`ingest()` 接受 `log_callback` 参数，engine 内部 `_log()` 辅助函数同时写 `logger.info()` 和 `log_callback`。`log_callback` 把日志写入 `_log_buffer`（Lock 保护），主线程 QTimer 每 100ms 消费。每个关键节点（解析/清洗/切片前后、批次写入）后调用 `_flush_logs()`（`progress_callback(-1,...)`）触发额外的 UI 刷新机会。
- **资源释放时机**：`SyncKnowledgeWorker.run()` 在 `finally` 中 `engine.close()` 后才 `emit sync_finished`，避免主线程 `reload_rag()` 与 worker 侧资源释放竞态。

### 4.3 RAG 检索流程

```
Agent tool_call: rag_search(query, top_k=3)
  │
  ▼
RagSearchTool.run(query)
  │
  ▼
RAGEngine.search(query, top_k)
  │
  ▼
VectorStore.search_with_rerank(query, top_k=3, candidate_multiplier=4)
  │
  ├─ VectorStore.search(query, top_k=12)
  │   ├─ _ef.embed_query(query)  ← 加 "search_query: " 前缀
  │   ├─ _normalize(query_vec)
  │   └─ table.search(query_vec).limit(12).to_list()
  │       → 转换 _distance 为 similarity ∈ [0,1]
  │
  └─ VectorStore.rerank(query, candidates, top_k=3)
      ├─ BGE reranker 可用: reranker.compute_score([[q, c["text"]]...], normalize=True)
      ├─ 不可用: 回退到距离分数排序
      └─ 按 rerank_score 排序取 top_k
```

**Token 控制**：默认 3 条结果，单次 ≤ 1500 tokens（32768 上下文中占比 < 5%）。

### 4.4 上下文收缩流程

```
触发条件:
  (a) 主动: _estimate_history_tokens() > 0.9 * max_context_tokens
  (b) 被动: LLM 抛 context_length_exceeded 错误

_shrink_context(reason):
  │
  ├─ 若 history ≤ keep_recent + 2: 跳过（不值得摘要）
  │
  ├─ old_messages = history[:-6]
  │   recent_messages = history[-6:]
  │
  ├─ 修复悬挂 tool 消息:
  │   while recent_messages[0].role == "tool":
  │     recent_messages.insert(0, old_messages.pop())
  │
  ├─ transcript = _format_messages_for_summary(old_messages)
  │   (每条消息截断到 2000 chars，防止摘要 prompt 超预算)
  │
  ├─ summary = _summarize_via_llm(summary_prompt)  ← 失败回退 _fallback_summary
  │
  ├─ _append_summary_to_memory(summary, reason)
  │   (原子写 workspace/memory.md，带时间戳)
  │
  ├─ history = [summary_msg(role=user)] + recent_messages
  │
  └─ on_context_shrunk(summary, reason)
```

### 4.5 工具分发流程

```
LLM done event → tool_calls = [{id, function: {name, arguments}}]

for tc in tool_calls:
  ├─ args = parse_args(raw_args)  ← JSON 解析
  │   失败: on_tool_start(name, {_raw_arguments}) + on_tool_end(name, ToolResult(False, error))
  │
  ├─ tool = registry.get(name)
  │   不存在: on_tool_start + registry.execute (返回 unknown tool 错误) + on_tool_end
  │
  ├─ needs_confirm = tool.should_confirm(args)
  │   True 且用户拒绝: on_tool_end(name, ToolResult(False, "User denied"))
  │   (不调 on_tool_start — "never started" 语义)
  │
  └─ on_tool_start(name, args)
     result = tool.run(**args)
     on_tool_end(name, result)
     history.append({role: tool, tool_call_id: tc.id, name, content: result.to_message()})
```

### 5.2 线程同步原语

| 位置 | 原语 | 用途 |
|------|------|------|
| `BridgeCallbacks` | `threading.Event` × 2 | `confirm` / `ask_user` 阻塞 worker，等 UI 设置结果 |
| `BridgeCallbacks` | `threading.Lock` | 保护 `_confirm_result` / `_ask_result` |

| `RAGEngine` | `threading.Event` (`_cancelled`) | 协作式取消 |

### 5.3 阻塞对话协议（confirm / ask_user）

```
Worker 线程                         UI 主线程
─────────                           ─────────
callbacks.confirm(msg)
  ├─ _confirm_event.clear()
  ├─ bridge.confirm_request.emit(msg)  ──→  _on_confirm_request(msg)
  └─ _confirm_event.wait(timeout=600)      ├─ QMessageBox.question(...)
                                            │  (UI 阻塞等用户点击)
                                            └─ set_confirm_result(reply == Yes)
                                                  ├─ _confirm_result = val
                                                  └─ _confirm_event.set()
  ← 被 set 唤醒
  return _confirm_result
```

- 超时 600s，避免 worker 永久卡死。
- `cancel()` 同时 set 两个 Event，让阻塞中的 `confirm`/`ask_user` 立即返回。

### 5.4 信号命名陷阱

`SyncKnowledgeWorker` 自定义信号以 `sync_` 前缀（`sync_finished` / `sync_failed` / `sync_progress`），**不能**命名为 `finished` —— 会遮盖 QThread 内置的 `finished` 信号，导致 `deleteLater` 在 `run()` 内部触发而清理却在 `finished`（run 返回后）才连接的悖论。

### 5.5 技能建议的延迟显示

`on_skill_suggested` 在 agent run 期间到达，但**不在 streaming 过程中弹模态对话框**（会阻塞 UI 事件循环，导致 content/reasoning chunk 无法渲染）。技能建议被缓存到 `_pending_skill`，在 `_on_finished` 之后（worker 线程已 join）才显示对话框。

## 6. 资源管理

### 6.1 资源生命周期

```
资源                          所有者                    释放时机
────────────────────────────  ──────────────────────  ─────────────────────────────
httpx.Client                  LLMClient                LLMClient.close() / _rebuild_agent
LanceDB connection            VectorStore._db          VectorStore.close() (置 None)
LanceDB table handle          VectorStore._table       VectorStore.close() / reload()
FastEmbed ONNX InferenceSession  VectorStore._ef      VectorStore.close() → session.release()
BGE reranker (PyTorch model)  VectorStore._reranker    VectorStore.close() → model.cpu() + 置 None
MCP subprocess                MCPClient._process       MCPClient.stop() → terminate + kill
RapidOCR engine (global)      _OCR_ENGINE              进程退出时释放（全局单例不显式 close）
RAG engine                    ToolRegistry._rag_engine  ToolRegistry.shutdown() → engine.close()
QThread workers               MainWindow               closeEvent() → wait(timeout) → terminate()
```

### 6.2 显式释放的必要性

Python GC 无法及时回收以下 C++ 资源：
- **ONNX Runtime InferenceSession**（~130MB embedding + ~500MB reranker）：引用计数 + 循环 GC 才会触发析构，期间内存不释放。
- **LanceDB 连接**：持有文件句柄和 mmap。
- **MCP 子进程**：不 stop 会变成僵尸进程。

因此 `VectorStore.close()` 显式：
1. 调用 `InferenceSession.release()` 立即回收 C++ 堆。
2. `model.cpu()` 把 PyTorch tensor 移出 GPU。
3. 置 None 让 Python 引用消失。

### 6.3 `_rebuild_agent` 的清理顺序

应用配置时重建 agent：
1. `old_agent.tools.shutdown()` — 停 MCP 子进程、关 RAGEngine。
2. `old_llm.close()` — 关 httpx 连接。
3. 创建新 `LLMClient` + `Agent`。

**运行期间禁止重建**：`_on_apply_config` 检查 `_busy`，若 agent 正在运行则弹窗拒绝（否则会销毁正在使用的 tools/httpx）。

### 6.4 窗口关闭清理（`closeEvent`）

对每个 QThread worker：
1. `disconnect()` — 断开所有信号，让 emit 变 no-op。
2. 协作式 `cancel()`（若支持）。
3. `wait(timeout)` — 等 run 返回。
4. 仍存活则 `terminate()`（最后手段，不安全）。

之后：
- `agent.tools.shutdown()` — MCP 子进程 + RAGEngine。
- `llm.close()` — httpx 连接。

### 6.5 RAG 资源竞态与解决

**问题**：`SyncKnowledgeWorker` 写完数据后，agent 的 `RAGEngine` 持有 stale 表句柄，看不到新数据。

**解决**：
- `SyncKnowledgeWorker.run()` 在 `finally` 中 `engine.close()` 释放 worker 侧资源后，才 `emit sync_finished`。
- UI 收到 `sync_finished` 后调用 `agent.tools.reload_rag()`，触发 `RAGEngine.reload()` 丢弃表句柄，下次操作重新打开。

### 6.6 日志控件并发崩溃与解决

**问题**：同步期间，`QSignalLogHandler` 的 queued signal 和 QTimer 轮询的 `appendPlainText` 同时操作 `log_view`，导致 PyQt6 内部断言失败调用 `abort()` 崩溃。

**解决**：
- `QSignalLogHandler._sync_active` 标志：同步开始时设为 `True`，`emit()` 中跳过 RAG 模块日志（`_RAG_LOG_PREFIXES` 匹配），避免与 QTimer 轮询竞争。
- 同步结束后恢复为 `False`，`QSignalLogHandler` 重新接管 RAG 日志。
- `_log_buffer` 用 `threading.Lock` 保护，确保多 worker 线程写入与主线程消费的原子性。

## 7. 错误处理

### 7.1 错误传播路径

```
工具层错误
  ├─ Tool.run() 抛异常 → ToolRegistry.execute 捕获 → ToolResult(False, error)
  └─ ToolResult 通过 on_tool_end 回调 → UI 显示，并写入 history 作为 tool message

Agent 层错误
  ├─ LLM stream 异常:
  │   ├─ context_length_exceeded → 被动收缩重试（最多 3 次）
  │   └─ 其他 → on_error + on_finished, 退出 run()
  ├─ parse_args 失败 → 报错给模型（写入 history），继续下一轮
  └─ 达到 max_iterations → on_finished, 返回当前 final_content

UI 层错误
  ├─ _rebuild_agent 失败 → on_error 弹窗
  ├─ sync 失败 → sync_failed 信号 → QMessageBox.critical
  └─ worker 异常 → bridge.error 信号 → _on_error 显示

RAG 层错误
  ├─ 单文件 extract 失败 → 记录到 stats["errors"], 跳过该文件
  ├─ 单文件 clean/chunk 失败 → 记录 + 跳过
  ├─ VectorStore add 批次失败 → 记录, 单批失败不中断（连续 ≥3 批才中断）
  └─ manifest 更新失败 → 警告日志, 不影响已写入的向量

MCP 层错误
  ├─ 命令不存在 → MCPError, ToolRegistry 跳过该 server
  ├─ 请求超时 → MCPError
  ├─ 子进程崩溃 → reader 线程退出, pending 请求回填错误响应
  └─ JSON 解析失败 → 警告日志, 跳过该行
```

### 7.2 防御性设计

- **JSON 持久化**：所有 `_JsonStore` 加载时 `try/except (OSError, json.JSONDecodeError)`，损坏文件回退到 `{}`。
- **类型防御**：`LongTermMemory` / `SkillManager` 加载后 `isinstance` 检查，None 重置为 `[]`。
- **config 迁移**：`_migrate()` 把过期的 embedding 模型名 / 过小的 `max_tokens` 自动升级到当前默认。
- **空操作回退**：`on_context_shrunk` 等回调用 `try/except` 包裹，避免 UI 异常影响 agent 循环。
- **悬挂消息修复**：`_trim_history` 和 `_shrink_context` 都确保 history 不以 `tool` 消息开头。

## 附录 A：关键性能优化

1. **流式 token 速度估算**：增量计数 `live_est_tokens += _estimate_tokens(chunk)`，每 0.3s 发射一次；总开销 O(N) 而非 O(N²)（避免每 0.3s 全量 join + 扫描）。
2. **TTFB 排除**：速度计算用 `gen_elapsed = now - ttfb`（不含 prefill 延迟），准确反映生成速度。
3. **chunker 增量计数**：维护 `cur_cjk` / `cur_other` 运行计数，避免 O(N²) 重复扫描。
4. **RAG 流式 ingest**：worker 池并行 + 有界队列背压 + 批量 embed，内存占用 O(workers × 单文件 chunks) + O(batch_size)，不随知识库总规模线性增长。
5. **OCR 全局单例**：4 worker 共享同一 RapidOCR 实例（~500MB），通过信号量串行调用，避免 ~2GB 重复加载。
6. **LanceDB 表不缓存"不存在"**：`_ensure_table()` 每次重查 `table_names()`，因为 SyncKnowledgeWorker 可能已创建表；目录 listing 很便宜。
7. **`list_sources` 用 pyarrow compute**：在 Arrow 层去重，避免把全部行转 Python 对象。
8. **子批次嵌入释放 GIL**：`_embed_chunks` 将每批 20 个 chunk 拆分为 5 条/子批，子批次间 `sleep(0.01)` 释放 GIL，让主线程 QTimer 能插入执行消费日志缓冲区，避免 ONNX Runtime 长时间持 GIL 导致 UI 冻结。
9. **QTimer 日志轮询**：同步期间用 100ms 间隔的 QTimer 直接在主线程事件循环中轮询 `_log_buffer`，绕过 Qt queued signal 机制（后者在 GIL 被占用时无法及时处理）。

## 附录 B：已知约束

1. **`code_run` 超时无法强杀线程**：daemon 线程的无限循环会持续到进程退出。本地工具可接受，但生产部署需注意。
2. **MCP 工具默认 destructive**：所有 MCP 工具需用户确认，无法细粒度区分安全/危险操作。
3. **单进程单 agent**：不支持多 agent 并发对话；`_history` 是实例属性，非共享。
4. **RAG 不支持增量删除单 chunk**：`delete_by_source` 删整个 source 的所有 chunk，无法精确删除单个 chunk。
5. **摘要 LLM 调用无超时**：`_summarize_via_llm` 复用 `chat_stream`，无独立超时控制（依赖 LLMClient 的全局 timeout）。
